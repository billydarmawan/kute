# Security policy

## Reporting a vulnerability

**Report privately, through GitHub:**
[**Report a vulnerability**](https://github.com/kute-dev/kute/security/advisories/new)

That form is private between you and the maintainer until an advisory is published.
Please use it rather than an issue, a discussion, or a pull request — kute's bug form
asks reporters to attach diagnostics that name their clusters and namespaces, and a
public issue is the wrong place to start a conversation about a vulnerability in a tool
that holds cluster credentials.

kute is maintained by one person. Expect an initial response within 7 days; if you
haven't heard anything by then, the report was missed rather than ignored — say so on
the same advisory thread.

If you'd like credit in the advisory, say so in the report and name how you'd like to be
credited.

## Supported versions

Pre-1.0, only the most recent release is supported. Fixes ship in a new release rather
than as patches to older tags.

## Scope

kute is a terminal client. It has no server, no hosted component, and sends nothing
anywhere except one update check against `api.github.com`, which
[`update.check: false`](README.md#configuration) disables.

**In scope** — anything that lets a third party reach the cluster or the credentials
through kute:

- Credential handling: kubeconfig parsing, exec credential plugins
  ([README § Authentication](README.md#authentication)), tokens in memory or on disk.
- Command construction for the verbs that shell out (`exec`, `logs`, port-forward,
  `kubectl debug` node shell) — argument injection through a resource name, namespace,
  or container name.
- Anything that causes a mutating verb to run against a different object than the one
  the confirm dialog named, or to run without its confirm at all.
- Anything that writes outside its documented paths, or writes credentials into a file
  that documents itself as not holding them.
- The update check and the installers (`install.sh`, `install.ps1`), including the
  integrity of what they fetch. Release archives are signed with a keyless cosign identity
  bound to the release workflow and carry a build provenance attestation —
  [`docs/verifying-releases.md`](docs/verifying-releases.md) is how to check one, and a
  verification failure you can't explain belongs on the advisory form above rather than in
  a public issue.

**Not vulnerabilities** — these are the tool working as designed, and reports about them
will be closed with a pointer back here:

- **kute can delete, drain, and restart things.** That is the product. The safety
  contract is the confirm tiers ([`README.md`](README.md#prodcontexts-and-destructive-actions)),
  not the absence of the verbs. A *bypass* of those tiers is in scope; their existence
  is not.
- **`--log-file` and crash reports contain context, cluster and namespace names.** This
  is documented ([`docs/diagnostics.md`](docs/diagnostics.md)), the files are written
  `0600`, and both are opt-in or crash-triggered. Credentials, tokens and Secret
  *values* in either file would be a vulnerability; names are not.
- **kute shows you Secret values when you press the key that shows Secret values.** It
  displays what the API server hands back to your own identity. If you can read it with
  `kubectl`, kute showing it is not an escalation.
- **Anything requiring an attacker who already has your kubeconfig.** At that point they
  have the cluster; kute is not the boundary.
- Reports generated by a scanner against a dependency with no reachable call path.
  [`govulncheck`](.github/workflows/govulncheck.yml) runs in CI and is the bar — it
  reports reachability, not mere presence.

## Not a security issue?

Crashes, wrong renders, and everything else go to the
[bug form](https://github.com/kute-dev/kute/issues/new?template=bug_report.yml), which
asks for the crash report kute writes for you. See
[`docs/diagnostics.md`](docs/diagnostics.md).
