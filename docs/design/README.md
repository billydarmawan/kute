# Handoff: kute — Inverted Main-Screen Design

## Overview
A kute Kubernetes TUI: the full-width resource table is the only resting state, and navigation appears on demand via a jump palette (`g`). This replaces the previous persistent 3-pane (groups › kinds › resources) layout. The package covers the full decided surface: main table, jump palette (fuzzy + alias chips), error/disconnected states, pod detail, log view, namespace + context switching, help overlay, YAML view, destructive-action confirm, deployments + events, exec picker, first-run/empty states, nodes (list + detail), port-forwarding (picker + forwards manager + header chip), CRD support (discovered kinds, CRDs list, generic detail), loading states, incident timeline, YAML edit, scale, Helm releases, cluster overview, bulk operations (marked sets), secret decode, RBAC who-can, and ingress/Gateway-API routing tables, plus the 0.2.0 addendum: inline mutation editors (image/tag, resources, labels/annotations, configmap/secret data) and update notifications.

## About the Design Files
The file in this bundle (`Kute Spec.dc.html`, plus its runtime `support.js`) is a **design reference created in HTML** — a mockup showing intended look and behavior, not production code. It is the curated spec: one canonical mock per screen, organized in 17 numbered sections, no competing alternatives. The task is to **recreate these designs in the kute Go codebase** using Bubble Tea + Lip Gloss idioms. HTML px values are design-proportions; map them to terminal cells (see "Mapping HTML → terminal" below).

**Every screen in the file is decided — implement all of them.** Anchor ids (each has a visible badge): `#2a` `#12a` `#12b` `#6a` `#6b` `#7a` `#7b` `#5a` `#5b` `#9a` `#9b` `#11a` `#11b` `#8a` `#8b` `#10a` `#13a` `#13c` `#13d` `#14a` `#14b` `#14c` `#14d` `#4a` `#4b` `#4c` `#10b` `#10c` `#15a` `#16a` `#16b` `#17a` `#17b` `#18a` `#19a` `#20a` `#21a` `#22a` `#23a` `#23b`. Numbering is historical (exploration turns), not an order — follow the 12 section headers in the file. Rejected alternatives (a plain 2b/3a taxonomy palette without alias chips; a 13b inline forward grammar) were removed from this file — 12a/12b supersede the palette-on-open state, 13a supersedes the forward entry flow. 0.2.0 adds `#24a` `#25a` `#26a` `#27a` `#27b` `#28a` `#28b`, sourced from `v.0.2.0.dc.html`. 0.8.0 adds `#36a` `#36b` `#36c` `#36d` `#36e`, sourced from `v.0.8.0.dc.html`.

## Fidelity
**High-fidelity** for color, hierarchy, alignment, copy tone, and interaction model — recreate faithfully. Exact pixel sizes are approximations of a character grid; use the terminal's monospace metrics.

## Design Principles (apply everywhere)
1. Every screen shares one skeleton: **header bar · body · keybar** (and optional strip rows under the header). Errors are not a different-looking app.
2. **Data by default, navigation on demand.** No persistent nav chrome; location lives in the header breadcrumb.
3. **Never blank out data the user already has** — stale data is shown desaturated with an age stamp.
4. Errors are **inline and actionable** (retry keys, copy-error, switch context), never modal dialogs that block browsing.
5. Keybar always reflects the current mode and only shows applicable keys, grouped by intent with `│` separators; modes get a colored pill (FILTER / GOTO / OFFLINE / NO CLUSTER).

## Screens / Views

### 2a — Main table (resting state)
- **Purpose:** the default screen; 100% of body pixels on live resource data.
- **Header bar** (bg `#0e0e15`, bottom border `#26263a`): app wordmark `kute` in the plain bright text token `#f0f0fa` (`#14141c` light, bold) `│` (extra trailing space after the bar, unglueing the leading `c` from the wordmark) `c` context `microk8s-cluster` (`#9a9ab2`) `›` `n` namespace `nva-stage` (`#d8d8e8`, one step brighter than context) `›` `g` kind `Pods` (bold `#f0f0fa`) — the path steps up in brightness toward the current kind so depth reads at a glance. (Implementation deviation: the mockup's brand-green `❯` chevron prefix was dropped — `kute` renders on its own.) The `c`/`n`/`g` prefixes live on the breadcrumb segment each one changes, in their own muted purple `#7c6bb0` (`#8a7fac` light) — duller and unbolded next to the keybar's own brighter `#a78bfa`/`#6b46d9` key hints, so they read as wayfinding rather than actions and recede behind the path text — no separate hint text. Right-aligned: `sync 2s` (dim) and connection status `● connected · 12ms` (green `#34d17b`).
- **Health strip** (bg `#0c0c12`, border-bottom `#1c1c2c`): per-status counts — `● 32 running` (green dot), `▲ 2 pending` (yellow `#e8c74a`), `✕ 1 crashloop` (red `#ef6a6a`), `○ 1 completed` (blue `#6aa8ef`); numbers in `#d8d8e8`, labels dim. Right: `36 pods · 3 nodes`.
- **Table columns:** status dot (2ch) · NAME (flex, ellipsize) · RDY (5ch) · STATUS (13ch) · ↺ restarts (4ch) · CPU (bar+pct) · MEM (bar+pct) · NODE (9ch) · AGE (right-aligned, 4ch). Column headers uppercase, `#55556e`, letterspaced; sort indicator `↑`/`↓` in purple next to sorted column.
- **Manual sort (1-9):** digit keys pick a column by position (1 = first data column past the status dot) on every kind's own table — first press sorts ascending, pressing the same digit again flips to descending, a different digit switches columns at its own natural first direction. Metrics/counts/recency columns (Restarts, CPU, MEM, Age, and anything else rendered right-aligned as numeric — Data, Replicas, Completions, Active, Capacity, Traffic, Rev, Updated) default descending-first (busiest/most/most-recent first); everything else (Name, Status, Node, Ready, ...) defaults ascending-first. A CPU/MEM sort stays live across the 2s metrics poll. No-op in the all-namespaces grouped view (6b) — namespace partitioning owns row order there, and the arrow stays hidden the same way it already does for the built-in default. Resets back to the built-in default (unhealthy-first, CRD's group-then-name, etc.) whenever the kind or namespace changes.
- **Rows:** 1 line each. Status dot and STATUS text share the status color (Running green, Pending yellow, CrashLoopBackOff red, Completed blue). Names `#d8d8e8`; crashlooping pod names tinted `#f0b7b7`. Restarts > 0 render yellow, otherwise dim. CPU/MEM: mini bar (track `#1c1c2c`, fill purple, fill yellow when ≥70%) + small pct in dim; `–` when metrics unavailable.
- **Selected row:** bg `#1d1633`, left border 2px/1ch purple `#a78bfa`, name brightens to `#f0f0fa`.
- **Footer of table area:** `1–9 of 36` + scrollbar glyphs (`▐▌░░░░`) in `#44445c`.
- **Keybar** (bg `#0e0e15`, top border `#26263a`): `g goto · / filter │ ↵ open · l logs · d describe · e exec │ n namespace · c context` … right: `? help`. Keys purple, labels dim.

### 4a — Connection lost mid-session
- Header status becomes `◌ disconnected` (red).
- **Error banner** under header (bg `#2a1518`, border-bottom `#4a2228`): `▲` red icon, verbatim error `watch stream lost · dial tcp 10.0.0.5:16443: i/o timeout` in `#f0b7b7`; right: `retry 3 · next in 4s` (`#c98a8a`) + keys `r retry now`, `c switch context` (keys `#ef8a8a`).
- **Stale strip** replaces health strip: `⧗ showing snapshot from 10:24:31 · 94s old` in yellow; right `counts frozen · 36 pods`.
- **Table:** identical layout, rendered desaturated/dimmed (HTML uses saturate(0.35) + 66% opacity; in terminal, substitute the dimmed color ramp — e.g. statuses drop to muted variants, text one step darker). Browsing/selection still works.
- **Keybar:** `OFFLINE` pill (bg `#2a1518`, text `#ef8a8a`), keys `r retry · c context · ↑↓ browse snapshot`; right note `mutating actions disabled`. Delete/exec/edit verbs are disabled while offline.
- Auto-retry with visible countdown and attempt counter; `r` retries immediately.

### 4b — RBAC / API error on one kind (403)
- Header stays green/connected — the error is scoped to the kind, not the app.
- **Body:** centered card (bg `#16121a`, border `#3a2a30`, radius): title `403 Forbidden` (red, bold) + `secrets.v1 · list` (dim). Verbatim message with entity names highlighted in yellow: `User "dev-readonly" cannot list resource "secrets" in namespace "nva-stage"`. Below a divider, recovery actions each on one line: `g jump to another kind — everything else still works`, `c switch context — prod-eks grants secrets:list`, `y copy error — paste to your cluster admin`, `r retry`.
- Under the card: `last successful list: never · RBAC errors are not retried automatically` in `#44445c` — `never` only when this kind/namespace has never listed; after a good list it reads `last successful list: 10:24:31 (94s ago)`.
- **No auto-retry on 4xx** — auto-retry is reserved for network failures (4a).
- **Namespace-scoped hint:** when a namespace is known (a kind/namespace is already selected) and the session isn't already running `--namespace-scoped`, one more line names it — `kute --namespace-scoped=<ns> may see more, if that namespace grants it` — since a cluster-wide 403 is exactly the shape a namespace-bound identity (a `Role`, not a `ClusterRole`) hits on a plain launch (`docs/lazy-informers.md §5.6`). Omitted for a session already scoped, or before any namespace is known.

### 4c — Cluster unreachable at launch
- Header: context name + `◌ connecting failed` (red). No data exists, so recovery paths ARE the screen (centered, ~58% width):
  - Title row: `✕ microk8s-cluster is unreachable` (bold) + right `retrying in 8s · attempt 2`.
  - Raw error in a red-tinted box (bg `#16121a`, border `#3a2a30`, text `#c98a8a`).
  - `SWITCH CONTEXT` section: bordered list of all kubeconfig contexts, **pre-probed in the background** with reachability + latency — `✕ microk8s-cluster (current · timeout)`, `● prod-eks (reachable · 32ms)` (selected), `● kind-local (reachable · 4ms)`. A sibling the server answered with a 403 on `/livez` reads `● <name> (reachable · 4ms · 403)`; one whose 401 or credential plugin failed reads `✕ <name> (needs login)` rather than unreachable. Failing context stays listed. **Credential-plugin contexts are not probed**, by the same rule as §7a: a sibling whose user mints its credential through an exec or auth-provider plugin reads `○ <name> (not probed)` in the faint neutral tone, not dimmed, and stays selectable — `↵` on it switches as for any other row, running its plugin as part of that switch. `r` retries the current context and re-probes the static-credential siblings, still leaving plugin ones alone, so the switch is the one way to try such a context.
  - Keys: `↵ connect to selected · r retry now · e edit kubeconfig path · ctrl+q quit`.
  - **One rebuild at a time:** `↵`/`r`/`e` do nothing while this screen's own reconnect is still running, and are refused with a red `✕ another context switch or reconnect is still running` line while a 7a `c` switch opened over this screen is; a `c` switch asked for while a reconnect runs is refused the same way, on the keybar (§7a). The two never run alongside each other.
- **Keybar:** `NO CLUSTER` pill + `probing other kubeconfig contexts in the background`.

### 5a — Pod full view (↵ on a table row)
- Breadcrumb extends: `… › Pods › nva-worker-9k2ss` (pod name bold).
- **Title row:** pod name (bold, 14px-equivalent = emphasized) · status `✕ CrashLoopBackOff` (red) · `↺ 6 restarts` (yellow) · right `watching · live` (dim).
- **Meta grid** (label over value): NODE / IP / QOS / CONTROLLER / AGE. Controller is a link (`deploy/nva-worker ↗` in purple) that jumps via the goto machinery.
- **Last-termination banner** (promoted to top, solid fill `#2a1518` with a `▌` left accent bar in `#4a2228` — no box border, since a 1-cell border glyph can't be tinted on its inner half alone and either bleeds the fill outside the stroke or leaves a gap inside it): `Last termination` (red bold) + `exit 137 · OOMKilled · 4m ago`; body line names the container (yellow) and the memory limit + next backoff. This answers "why is it broken?" first — never bury it.
- **Config-error banner** (same solid-fill `▌` shape as the termination banner, placed above it — it's the current reason, the termination is history): shown while any container is `Waiting · CreateContainerConfigError`. `Can't start container` (red bold) + `CreateContainerConfigError`; one body line per stuck container, `Container <name>: <kubelet message>` — the kubelet's own text already names the missing Secret/ConfigMap and key, so it is shown verbatim (wrapped, never clipped).
- **CONTAINERS:** grid, header row sandwiched by top/bottom rule lines (same treatment as the main table's own header) — status glyph · name · image (dim, front-ellipsized with a redundant `@sha256` digest dropped, per §10a's rule — the tag, or lacking one the digest, is the version signal and always survives at the end) · state (`Waiting · backoff` red / `Running` green) · restarts right-aligned. Conventional `spec.initContainers` render in a separate **INIT CONTAINERS** grid with the same columns; native sidecars stay in CONTAINERS because they keep running. `↑↓`/`j`/`k` move one selection across CONTAINERS, INIT CONTAINERS, and EPHEMERAL (not shown in the keybar — see below); the selected row's full-width background (gaps included, not just the cell text) highlights — never `tab`, which is reserved app-wide for panel/grid focus switches, not in-grid row movement. `l` opens logs for whichever container is selected, including a completed or waiting init container; `x` never offers a conventional init container as an exec target.
- **CPU/MEM bars**, inline on one line (`CPU ▮▯… 4m / 500m   MEM ▮▮… 246Mi / 256Mi`) with `used / limit` text, fenced above and below by the same rule-line treatment as the CONTAINERS header; MEM at 96% renders the bar and text red.
- **EVENTS (newest first):** grid — type (`Warning` yellow/red, `Normal` blue) · reason · age · message. Messages wrap verbatim; `pgup`/`pgdown` page the full detail body so an older diagnostic is never clipped away by the terminal height.
- **ENV & MOUNTS** (`v` toggles; hidden by default so the resting view stays lean, and the toggle survives `[/]`): sits under the container grids, above RELATED, and follows the container selection (`ENV & MOUNTS · <container>`). ENV lists only variables drawn from a Secret/ConfigMap — `NAME ← Secret/name · key`, then envFrom imports as `PREFIX* ← ConfigMap/name · all keys`; literal values and fieldRefs are never listed. MOUNTS lists every volumeMount, `/path (ro) ← <source>` (`Secret/x`, `ConfigMap/x`, `PersistentVolumeClaim/x`, `emptyDir`, `projected · …`, …, plus `· subPath p`). Names and keys only, never a value. Everything comes from the pod spec already in the cache — nothing is fetched. The `v env/mounts` hint appears only when the pod has something to show.
- **RELATED │ TOLERATIONS row** (full width, two columns, under the container grids and before EVENTS — replaces the old ~25%-width right sidebar; labels and annotations both live solely in `m`, the 26a editor, and the resting view never grows a LABELS or ANNOTATIONS section): RELATED on the left — the resolved parent controller (whatever kind the pod's owner chain resolves to: Deployment/StatefulSet/DaemonSet/Job/an unresolved ReplicaSet — the same value the meta grid's CONTROLLER field shows), then **the Flux reconciler that applied it** when there is one (read from the `kustomize.toolkit.fluxcd.io/*` / `helm.toolkit.fluxcd.io/*` labels on the pod, else on that controller — Flux labels what it applies, not the pods a controller creates later; a HelmRelease label wins over a Kustomization one; rendered `Kustomization/flux-system in flux-system` when it lives in another namespace, and only on a cluster serving that kind; its digit opens 31a's inventory rather than the list, since "what else did this apply" is the question the link answers), the PersistentVolumeClaims the pod mounts that still exist, the Services whose selector matches the pod, every Ingress that references one of those Services, when resolvable, and then the Secrets and ConfigMaps the spec references (volumes and projected sources, envFrom, env `valueFrom`, imagePullSecrets; Secrets first, each sorted by name; the injected `kube-root-ca.crt` is skipped). Secret/ConfigMap entries are named from the spec and **never checked against a cache** — a Secret read would start the cluster-wide Secret informer, and many users can't list Secrets — and they come last so they can't push workload/network links past the cap. Their digit opens the 27b/27a Data view directly (pushed over 5a, one `esc` back) rather than the list — each rendered `N Kind/name ↗` (purple link, `N` a 1-based digit in RELATED's own dim color) — pressing that digit jumps via the shared goto machinery, same as everywhere else it's used (9b events, 16b timeline, 23a routing table, …): a fresh browse view opens on the target with poddetail pushed beneath it, so one `esc` back returns here. Resolved once per load, not on keypress, so the digits on screen always match what pressing them does. Capped at 9 entries (the numbered jump is a single digit key). TOLERATIONS in the right column.
- **Keybar:** `l logs · x exec · 1-2 related │ D delete │ [/] next/prev pod · pgup/pgdown page · ? help` — page hints appear only when the body overflows; on a narrow overflowing screen the sibling hint is dropped, and the related hint drops once the body is paged away from the top, to keep page navigation and help visible. The related-item hint's key text tracks however many RELATED actually resolved (`1` when there's just the one). `esc back`, `[/]`, and the container grids' `↑↓` still work when omitted from the legend. `[/]` moves through the table's pod list **without leaving detail view**.

### 5b — Log view (l from table or detail)
- Breadcrumb: `… › nva-worker-9k2ss › logs · worker`; right status `▶ following` (green).
- **Toolbar strip:** `container worker (tab: metrics-sidecar)` · `since 15m` · `wrap on` · `timestamps on`; right: `12 WRN · 3 ERR in view` (counts colored).
- **Stream** (bg `#08080d`): `HH:MM:SS` timestamp `#44445c` · level token colored (`INF` green, `WRN` yellow, `ERR` red) · message `#8a8aa2`; ERR lines get message text `#f0b7b7` and a full-width red-tinted row (`#2a1518`) for the most significant one. **Restart boundaries** drawn inline as a centered rule: `─── container restarted · restart 6 · 10:24:02 ───` in `#55556e`.
- Bottom status line: `▶ live · 2 new lines/s` (green) with cursor.
- **Behavior:** follow by default; scrolling up auto-pauses, `space` toggles; `w`/`e` jump to previous/next warning/error; `/` filters the live stream in place using the same filter grammar as the table; `tab` cycles containers; `s` changes since-window; `ctrl+y` copies the visible view.
- **Waiting-for-container state:** if the target container hasn't started yet (its pod-cache status is `Waiting`, e.g. `ContainerCreating`/`PodInitializing`/an image still pulling), the screen doesn't attempt to stream and error — it shows the wait instead, in the app's standing pending/not-yet-settled vocabulary (▲ `#e8c74a` amber, the same token 2b/11b/16b/19a/18a use for "in progress, not broken" — never the red of a genuine stream error): header status badge reads `▲ starting`; the toolbar strip reads `▲ waiting for container to start: ContainerCreating` with a right-hint `streams automatically once running`; the body keeps 5b's decorative loading bars, final line in the same amber naming the container and reason. No manual retry — streaming begins automatically the moment the container's cache-observed state changes to running.

### 6a — Namespace palette (`n`)
- Same palette shell as goto (2b), scoped to namespaces; opens over the dimmed table. Input prompt `ns ›`, right hint `microk8s-cluster · 6 namespaces`.
- **Columns:** selection glyph · NAMESPACE (current one tagged `current` in `#55556e`) · count column for the kind the table is currently showing (header names the kind — `PODS`, `DEPLOYMENTS`, `INGRESSES`, …; falls back to `PODS` for a cluster-scoped active kind — Nodes, Namespaces, Forwards — or before the first navigation) · HEALTH (inline colored glyph counts: `●32 ▲2 ✕1`, tallied for that same kind) · CPU share right-aligned (always pod CPU usage, independent of the active kind — metrics-server has no other kind's usage to report). Zero-count namespaces dim (`#44445c`) but stay listed.
- **`all namespaces` is a first-class last row** (blue `#6aa8ef`, glyph `∗`), separated by a top border — reached via `↑↓`/`↵`, not a dedicated key: `a` types into the query like any other letter, so filtering to a namespace starting with "a" isn't shadowed by an all-namespaces jump.
- **RECENT row:** last-visited namespaces. Opening the palette pre-selects the most recently visited *other* namespace (alt-tab semantics, like editor Ctrl-Tab), so `n ↵` — the same two keystrokes as the old double-tap — toggles straight back to it; typing goes anywhere else.
- **Numbered recent pick:** current and the immediately-previous namespace (the row tagged `previous` — the alt-tab target above) are both excluded from the numbered pick and from the RECENT row's own list: each already has its own on-row tag, so a digit for either — or repeating either in RECENT's text — would be redundant. Every recent namespace *after* that gets a 1-based digit, most-recent-first, capped at `1`-`9`. The digit renders directly on the row itself, in the same leading gutter cell the selection arrow occupies — the row IS the legend, no separate lookup needed. Typing that bare digit as the query's only character jumps `Sel` straight to it and shows a "`↵` switches to *name*" footer; it's a tentative selection, not an instant jump — `↵` still commits it. Any further typed character makes the digit "just the query's first character" again and reverts to plain fuzzy filtering, so e.g. `2048` still filters to a namespace named that. Same grammar as 7a's.
- **Recents float to the top** of the empty-query list, ahead of the rest (which keep their existing order): current first, then `previous`, then the numbered `1`-`9` recents in digit order — regardless of where they'd otherwise sort alphabetically. Once a query is typed, ordinary fuzzy-match ranking takes over instead. `all namespaces` still stays pinned as the last row regardless.
- Switching keeps kind + filter. Keys: `↵ switch · ↑↓ move · 1-9 recent · esc close`.
- **Denied state** (`docs/lazy-informers.md §5.6`): when this identity may not list Namespace at all — the common shape under `--namespace-scoped` — the same shell swaps its results area for a notice (`✕ cannot list namespaces`) instead of hanging on "loading namespaces…" forever (a denial never syncs). The input's placeholder relabels to `switch to`; RECENT and a `currently <ns>` footer still render, so there's still orientation even with nothing to browse. `↵` on the typed text dispatches straight to that namespace, unvalidated (there's no list to check it against) — same as always for a namespace typo. Keys collapse to `↵ switch · esc close`; no `↑↓`/`1-9`, since there's no list to move through (typed recents still work by name).

### 6b — All-namespaces mode
- Header scope segment renders `∗ all namespaces` in blue — scope is never ambiguous. Health strip shows cluster-wide counts + `125 pods · 6 namespaces`.
- **Rows grouped by namespace** (no NAMESPACE column): group header line (bg `#0e0e15`) = `▾` + namespace name (`#c4b5fd`) + pod count + right-aligned trouble chips (`▲2 ✕1`).
- **Triage default:** unhealthy pods first within groups; fully-healthy namespaces collapse to a single line (`▸ nva-prod · 54 pods · all running` in green). Partially-shown groups end with `+ N running · ↹ expand` in `#44445c`.
- Keys: `↹` expand/collapse group · `↵` open · `n` namespace palette · `N` jump into the selected pod's namespace (scoped mode, pod still selected). Keybar pill `ALL NS` (bg `#12203a`, text `#8ab8ef` — blue, not purple).

### 7a — Context palette (`c`)
- Third instance of the palette shell, one breadcrumb level up. Prompt `ctx ›`; right hint `~/.kube/config · 5 contexts`.
- **Columns:** glyph · CONTEXT (current tagged) · NAMESPACE (the context's remembered namespace) · STATUS right-aligned.
- **Reachability probed lazily on open:** `● 12ms` green, `◌ probing…` yellow, `✕ unreachable` red (row dims but stays selectable). A probe the server *answered* is not unreachable: a 403 on `/livez` reads `● 12ms · 403` green, and a 401 or a credential plugin that couldn't mint a token reads `✕ needs login` red (dimmed like unreachable). **Except credential-plugin contexts:** a context whose user mints its credential through an exec or auth-provider plugin (`aws eks get-token`, `gke-gcloud-auth-plugin`, kubelogin, …) is not probed on open, since probing it runs that plugin — which can pop a browser login or an SSO prompt for a context the user never picked. Its row reads `○ not probed` in the faint neutral tone, not dimmed, and stays selectable; the active context is probed regardless (it's already connected). `ctrl+r` is the explicit ask: it re-probes every context, plugin ones included. Choosing one with `↵` runs its plugin as part of the switch itself.
- **PROD tag** (border `#4a2a2a`, text `#ef9a9a`, 10px) comes from a kubeconfig annotation — it drives the 8b confirm escalation. (Implementation deviation, mvp-plan.md decision #2: sourced from `~/.config/kute/config.yaml`'s `prodContexts` list instead, never a name heuristic. A config file that doesn't parse fails closed: valid keys are salvaged, an unreadable `prodContexts` tags every context PROD, a persistent header chip says so, and `ctrl+p` refuses to overwrite the file, saying why in the palette footer.) Opening the palette pre-selects the most recently visited *other* context (alt-tab semantics), so `c ↵` toggles straight back to it. `ctrl+r` re-probes; `ctrl+p` marks/unmarks the selected context PROD — both chords, not bare letters, so `r`/`P`/`p` keep reaching the fuzzy query (`prod`, `staging-eu-north` and every `arn:…` context contain an `r`; a context can be named `Prod-EKS`) — writing straight back to that config file (only the `prodContexts` key, re-read from disk at write time and replaced atomically, so comments, unknown keys, later hand edits and per-invocation flags like `--no-update-check` are never clobbered or persisted) so it's picked up by every other kute session reading it, and the palette stays open with the toggled row still selected.
- **RECENT row + numbered pick:** same as 6a's — last-visited contexts on a RECENT row (current and the `previous`-tagged context excluded, same redundancy rule), each remaining one also carrying its digit directly on the row (leading gutter cell), and typing a bare `1`-`9` jumps `Sel` to that entry with a "`↵` switches to *name*" footer, degrading back to plain fuzzy filtering the moment a second character arrives.
- **Recents float to the top**, same as 6a's: current, then `previous`, then the numbered `1`-`9` recents in digit order, ahead of every other context (which keep their existing order) — only in the empty-query state; a typed query ranks by fuzzy match instead.
- Each context remembers its own namespace + kind + filter; switching restores them. Keys: `↵ switch · ↑↓ move · 1-9 recent · ctrl+r re-probe · ctrl+p mark prod · esc close`.
- **While a switch runs** (it can take up to ~30 s: the target's cache sync, plus a rollback to the original context if that fails) the screen you switched from stays up, and the header's connection badge reads `⣾ switching…` — the shared loading spinner in the `◌ probing…` status's yellow (`Warn`) — in place of `● connected`. **A failed switch is said on the keybar** through the same result-line path as every mutating verb (§8b): `✕ couldn't switch to <context>: <reason>` in red (`Bad`), folded onto one line and truncated with `...`, lasting until the next key — whether it failed before anything was torn down (a context whose client can't be built) or after, with the original context rebuilt. Never a modal or banner. A switch asked for while another switch or a 4c reconnect is still running is refused up front, before anything changes, and reported the same way (`… another context switch or reconnect is still running`).

### 8b — Destructive-action confirm (`D` delete)
- **Two tiers of friction:** non-prod contexts = inline `y/N` prompt in the keybar (no modal). PROD contexts (tag from 7a) = centered modal with **type-the-name confirmation**; `↵` stays dead until the typed name matches (show `7/16` progress in `#44445c`).
- Modal: **the only red-bordered surface in the app** (border `#5c2a2a`; header bg `#1a1014`, title `✕ delete pod` red bold, `PROD CONTEXT` tag right).
- Body answers "what actually happens": owner (`Deployment/nva-worker — will be recreated` in green), grace period (`30s`), and the harder chord for force delete (`ctrl+k`, grace 0).
- **Force delete is always the type-the-name modal**, PROD or not: `ctrl+k` on a Pod's inline `y/N` re-opens the confirm as this modal (title `✕ Force delete <pod>?`, no PROD tag outside PROD); inside the PROD modal it switches the verb and keeps the typed progress. The chord is a modifier so it can never be a typed character. The key and the modal's hint both render from the verb registry (`verbs.ForceDelete`).
- **Cascade-scope kinds are always modal:** deleting a Namespace (everything in it), a CRD (every instance, 14b) or a Node (every pod bound to it, DaemonSets included — strictly more than a drain) gets the type-the-name modal even outside PROD — and, for a marked set, 20a's type-the-count modal. One resolver (`verbs.TierForDelete`) decides this for every delete surface.
- Keys: `↵ delete (when name matches)` (key rendered red) · `esc cancel`. Keybar pill `CONFIRM` (bg `#2a1418`, text `#ef9a9a`).
- **The answer lands where the question was asked — the keybar — for every mutating verb on every screen** (delete, force delete, cordon, drain, rollout restart, rollback, suspend/resume, sync/refresh, renew, replace): a failure replaces the key hints with `✕ <action> failed: <server's error>` in red (`Bad`), truncated with `...`, never dropped, and stays until the next key — a drain blocked by a PodDisruptionBudget leaves the node cordoned and half-drained, which is exactly what must not pass silently. A success shows `✓ <action>` in green (`Good`) on the keybar's right, with the hints kept, until the next key. A refusal before anything runs (OFFLINE, missing target) reads the same as a failure. Writes run with no deadline — cancelling one mid-flight doesn't un-apply it — so a write still in flight after 1 s says so in the same right-hand slot, hints kept: `◌ drain node/node-a · still running · 4s` in `TextDim`, the verb's registry label and a kubectl-style target, its elapsed time advancing once a second until its own `✓`/`✕` replaces it (hidden under an open confirm; a write that lands inside the second never shows it). Screens whose editor has its own inline result line (26a, 24a/25a, 27a/27b, 36d) show it there instead, never twice.

### 11b — Node detail (↵ from nodes list)
- Same detail recipe as 5a: facts panel · related-objects table · keybar.
- **Top half, two columns:** CONDITIONS — each line leads with a status glyph (`●` healthy/inactive-pressure, `▲` active pressure, `✕` NotReady); label text dims even when its glyph is green (Ready, inactive pressure) — only an *active* problem (pressure true, NotReady) colors the label itself too. No `true` word is ever shown; inactive conditions show a dim `false`. Active pressure appends kubelet message + age in a dimmer tone than the yellow label. │ two allocation groups + TAINTS. **REQUESTED / ALLOCATABLE** (cpu/mem/pods) is the scheduling statement: the pods' *effective* requests — native sidecars, the init-phase peak, `spec.overhead`, pod-level `spec.resources` and in-flight in-place resizes included, the same rule `kubectl describe node`'s "Allocated resources" uses — against what the scheduler may still hand out. **USED / CAPACITY** (cpu/mem) is the live statement: this node's metrics-server usage against the whole machine, the same number 11a's list shows for it. Both render as bar + `used / total` text, hot values yellow. The two groups are deliberately separate and separately titled — they are different numbers, and showing only one of them under a bare `MEM` label is what made 11a and 11b look like they contradicted each other. USED / CAPACITY also carries a **disk** row under mem: the node's root filesystem (`node.fs` — the one the DiskPressure/nodefs eviction signal watches) used over its size, read from the kubelet summary API through the API server's node proxy, since metrics-server has no disk figure. It is a per-node read of the node on screen only, refreshed every 30s (the kubelet's own fs stats move on a ~1 min housekeeping cycle), and degrades independently of cpu/mem: `disk — reading kubelet stats…` before the first answer, `disk — no access (needs get nodes/proxy)` on Forbidden (which also stops the reads), `disk — kubelet stats unavailable` when the proxy call fails before any reading has landed — a later failure keeps the last good figure. When the container runtime's imagefs (images + writable layers) is a **separate filesystem**, an `img` row follows disk — filesystem fill against its size, the figure the `imagefs.available` eviction signal watches, since DiskPressure alone doesn't say which disk tripped. The summary API names no device, so "separate" means a different capacity, or the same capacity with free space more than 1% apart; a single-disk node reports imagefs as the same filesystem and gets no row. No reading: the USED group degrades to a dim note rather than a flatlined zero bar, naming why — `cpu / mem — no metrics-server installed` only when the metrics.k8s.io API isn't served, `… not permitted to read metrics-server` on Forbidden, `… metrics-server unavailable` for any other failure, `… no reading for this node yet` when metrics-server answered without this node; a failed poll after a good one keeps the last good reading, as disk does (19a's CAPACITY applies the same rule); a resource whose capacity the kubelet hasn't reported shows the bare figure rather than `N / 0`. On a short terminal the group's blank separator lines collapse first, and if the right column still doesn't fit the panel grows into the pods table (never below one visible pod row) rather than clipping, so TAINTS always survives.
- **Bottom half: the node's pods** — 2a's own Pods-list table widget (same per-status glyph/color derivation, live CPU/MEM mini-bars, RDY ratio, restart/crashloop tinting, and header-rule divider), filtered to this node and **sorted unhealthy-first then name**, the same order 2a's own Pods list uses. Columns: glyph · NAME · RDY · STATUS · ↺ restarts · CPU · MEM · NAMESPACE · AGE — NODE is dropped (every row is already this node) in favor of NAMESPACE, since a node's pods span namespaces. A health-strip line (2a's own "● N running · ▲ M pending · ✕ K crashloop" shape, tallying just this node's pods) sits directly above the table, its own horizontal rule separating it from both the facts panel above and the column headers below — the same strip/table rule treatment 2a uses. **Footer:** 2a's own `1–N of M` + scrollbar-glyph pagination line under the table. `↵` opens the pod (5a) — node → culprit → detail is three keys.
- Keys: `↵ open pod · C cordon · ctrl+d drain · e node events · esc back`. Keybar pill `NODE`.

### 13a — Port-forward picker (`f` on a pod/service/deployment row)
- Same small centered panel recipe as the exec picker (10a). Header: `⇄ forward › <object>` + `pod · nva-stage · 2 ports`.
- Columns: status glyph · PORT · NAME (+ `container <name>` in `#55556e`) · LOCAL right-aligned. Ports come from containerPorts (pods), spec.ports (services), or the pod template (deployments).
- **Local port is edited in place** on the selected row (`localhost:8080▎` with purple cursor) — no separate field. Pre-fills the first free port ≥ the remote (80 → 8080 since 80 is privileged; 9090 → 9090). If the pre-fill is busy, the row says so inline (`8080 busy → 18080`) and pre-fills the next free one.
- **A declared port is a hint, never a limit** — a container listening on a port it never declared is perfectly legal, and plenty are. So the panel always ends in a `+ other port` row (accent `+`, not the status dot) that takes a port nobody declared: `f`, `↓`, `3000`, `↵` works on a pod with no containerPorts at all, where this panel used to render `no forwardable ports found` and offer nothing. There is no empty state to reach.
  - Digits on that row open the **remote** (pod-side) port buffer, not the local one — the half that isn't known yet; the keybar's digit hint flips from `0-9 type local port` to `0-9 type port` to say which. The buffer takes kubectl's own spelling: one number derives the local by the rule above (`3000` → `localhost:3000`), `8080:3000` sets both. The pair is live — the will-run line and the LOCAL cell track every keystroke — and a left half is taken as given, busy or not, exactly like a local port typed on a declared row. An untyped or half-typed pair is refused with an inline keybar note (`type a port to forward`), never a forward aimed at port 0.
  - A Service/Deployment whose backing pod can't be resolved refuses the same way (`could not resolve a backing pod`) — the will-run line already said it, and starting would leave a session retrying a dial with no pod forever.
- `will run` line above the keybar: `kubectl port-forward pod/<name> 8080:80 -n <ns>` — copyable documentation, no magic. On `+ other port` it's the same line for the port you typed, or the prompt (`type a port the object doesn't declare — one, or local:remote`) until you do.
- Keys: `↵ start · type local port · ↑↓ port · esc cancel`. Single-port objects still show the panel (the local port is a real decision, unlike exec's shell).

- **Status derivation is conditions-based:** a Ready/Available-style condition maps to the standard glyphs (`✕ False` red, `▲ False`-but-Issuing yellow, `● True` green) and drives the summary strip (`status from Ready condition` noted right). Unhealthy-first sort + `+ N ready` collapse carry over.

- Verbs from the command registry — only generic ones apply: `↵ open · y yaml · e events · D delete · / filter`. Delete follows the 8b prod policy. Keybar pill = short kind name (`CERTS`).

### 14b — CustomResourceDefinitions list
- Cluster-scoped: namespace drops from the breadcrumb + `cluster-scoped` tag, same rule as Nodes (11a). Strip: `● 27 established · ▲ 1 installing` + `28 definitions · 9 API groups · sorted by group`.
- Columns: glyph · NAME (plural, lowercase) · GROUP · VERSIONS (served versions; deprecated ones dim) · SCOPE (`Namespaced`/`Cluster`) · COUNT (live instance count, right) · AGE.
- Status glyph = the CRD's **Established condition**; freshly-applied CRDs show `▲` until the API serves them. Zero-count kinds render dim.
- **`↵` jumps straight to that kind's instance list (14a)** — CRDs are a routing layer, like events. Keys: `↵ open instances · y yaml · / filter · g goto`. Keybar pill `CRDS`.
- Deleting a CRD deletes all its instances — it **always** gets the type-the-name modal (8b), even outside PROD. Namespaces and Nodes follow the same rule.

### 14c — Goto palette with discovered kinds
- Discovered CRD kinds join the fuzzy corpus **at connect time** (API discovery, cached per context) — no config, no plugin. `g cert` surfaces Certificates, CertificateRequests, ClusterIssuers.
- Type label's group slot carries the **API group** instead of a built-in category: `kind · cert-manager.io`; cluster-scoped kinds append `· cluster`. Custom resource **instance names** are searchable too (`api-tls` → `certificate · nva-stage` + `● ready`), same rule as pods, from the watch cache.
- **No alias chips for CRDs** — chips stay reserved for the ~8 built-ins (12a). A daily-used CRD earns rank in the untyped list via the same recency/frequency scoring as everything else.

### 14d — Generic custom resource detail (`↵` on any custom resource)
- Built only from what **every object has** — no CRD-specific layout code: title row (name · condition-derived status · apiVersion · `watching · live`), **meta grid from printer-column values** (ownerReferences and issuer-style refs render as purple `↗` links reusing the goto machinery, like 5a's RELATED), then:
- **CONDITIONS verbatim:** glyph · type · status · message · age. The message text IS the diagnosis (`Issuing certificate as Secret does not exist`) — never paraphrase it.
- **EVENTS (newest first):** the object's events, same grid as 5a.
- **If the object has no conditions and no events, `↵` skips this screen and opens YAML (8a) directly** — an empty detail screen is worse than the manifest.
- Keys: `esc back · j/k next/prev │ 1 owner │ y yaml · e events · D delete`. `1` (shown only when the object has an ownerReference) jumps to the OWNER link's object, like 5a's numbered RELATED entries. Keybar pill `DETAIL`.

### 15a — Loading a kind
- The **full shell paints in the first frame** — breadcrumb, column headers, keybar. Loading replaces only the rows, never the app.
- Header status: `⣾ loading pods · 0.4s` (yellow) — a counting timer, not a fake progress bar; on timeout 4c takes over. Strip: `⣾ listing pods in nva-stage…` + right `watch starts when the list lands`.
- Both marks are the **shared loading spinner**, not a static status glyph — an animating mark reads as live in the sub-second stretch before the timer's first decimal turns over. One spinner per screen drives both, so they animate in lockstep. Detail screens (11b, 23a) apply the same treatment to their own loading header/strip.
- **Skeleton rows** (7, fading opacity toward the bottom): gray pills (`#1c1c2c` name, `#16161f` cells) laid out on the exact column grid of the real table, so live data is a fill-in, not a relayout. Footer `– of –`.
- Nav keys (`g n c ?`) live immediately; row actions dark until rows exist (keybar says `row actions enable when data lands`).
- Revisiting a kind seen this session: **cached rows dimmed** (4a's stale grammar) instead of skeletons.

### 16a — Incident timeline (namespace, `t`)

### 16b — Incident timeline (object-scoped)

### 17a — YAML edit mode (`e` inside 8a)

### 17b — Scale (`+`/`−` on a deployment/statefulset row)

### 18a — Helm releases (registry kind, `g "hel"`)
- Shared list skeleton. Strip: `● 3 deployed · ◌ 1 pending-upgrade · ✕ 1 failed · ▲ 2 outdated` + `from sh.helm.release.v1 secrets`. Columns: glyph · RELEASE · CHART · LATEST · APP VER · REV · STATUS (failed carries the reason verbatim: `failed · hook timeout`) · UPDATED.
- **Browsing needs no helm binary** — decoded from release secrets in the watch. Only helm's default Secret storage driver is read, so 10c's empty state on this list says so (`releases kept with HELM_DRIVER=configmap or sql aren't listed`) rather than claiming the cluster has none. Mutating verbs (`R` rollback) shell out to `helm` with a `will run` line; helm missing from PATH explained inline. `R` on the list targets the previous revision and, on a first revision or a row whose release hasn't decoded yet, answers `nothing to roll back to` instead of confirming. On the `h` rail `R` targets the selected revision: dimmed and refused on the current one (it would only write an identical revision), and the confirm names the target's status, warning when it never went live (`· failed — not a known-good revision`).
- **Outdated is read-only, and says where it got its answer.** LATEST is the newest version of that chart in the user's *own local repo cache* (`repositories.yaml` + `<repo>-index.yaml`, parsed directly — no network on a browse path and no helm binary, same rule as the rest of the screen). A chart in no configured repo (locally built, OCI) reads `–`: an unknown, never a "you're current". Where two repos serve the same chart *name* they are usually two different charts (`fluent/fluent-bit` is on 0.x, `grafana/fluent-bit` on 2.x), so the answer is the newest version on the deployed release's own major series — picking "the highest number anywhere" would report a current release as several majors behind, and a false alarm is the one failure this signal can't afford. When no series matches, LATEST still shows the highest but marks it `12.2.1 ?`: a lead to check, not an assertion. An outdated row keeps its real helm STATUS — the strip still counts it `deployed` — and carries `▲` in the glyph column; outdated-ness is orthogonal to release health, not a fifth status. Freshness is the user's last `helm repo update`, so the strip names it rather than implying authority, and names it in *every* state — staying silent while the cache was fresh left no way to tell "checked, and you're current" from "never checked": `· repo cache 3h old` dim while it's fresh, and past a day `· repo cache 6d old — run helm repo update` in yellow, `· no helm repo cache — run helm repo add` when there's none. Naming the remedy is as far as this goes: kute can only see repos already in `repositories.yaml`, so there is no honest "add *this* repo" hint for a chart the cache has never heard of. The note outranks `from helm.sh/release.v1 secrets` at every width — both are caveats, but the source is the same on every render while the note is the one that varies and the one a user acts on, so a strip too narrow for both sheds the source (and, next, the remedy) rather than letting an all-`–` column stand with nothing saying why. `h` repeats the finding as one line above the revision rail.
- **Helm being finished is not the cluster being finished.** `helm upgrade` flips a release back to `deployed` as soon as it has applied its manifests — without `--wait` it never watches the rollout at all — so a release the user just upgraded reads `deployed` while its pods are still being replaced, and a green row is the one thing the screen shouldn't say there. A release with a workload still rolling carries 9a's rollout arrow `▸` in the glyph column, warn-yellow. Same rule as outdated, and for the same reason: helm's own word is what STATUS and the strip report (the release *is* deployed as far as helm is concerned), and the orthogonal signal rides in the glyph alone. Where a release is both mid-rollout and behind its repo, `▸` outranks `▲` — §19a already ranks a chart behind its repo as the least urgent thing on screen, and the rollout is the state changing under the user right now. The release→workload link is the release's own rendered manifest, not a label join: helm stamps nothing onto what it applies, and `app.kubernetes.io/instance` is a chart convention that any chart is free not to follow.
- `↵` opens release diagnostics: Helm's description and saved hook ledger are correlated with live objects and Kubernetes Events, followed by every object declared in the saved manifest. The summary strips wrap instead of truncating, as do the diagnostic table's SOURCE, HELM STATE, and LIVE EVIDENCE cells; RESOURCE stays a compact one-line identity. A pending hook whose Helm phase disagrees with newer cluster evidence is called out as a state mismatch; declared-but-absent objects say `not created`, never an empty-Pods claim. `y` on a row opens its saved release YAML, including hooks that cleanup policy or TTL already removed; `↵` on a live row uses shared goto navigation and `e` opens its object-scoped events. Only the kinds actually named by this release plus Events are read, preserving lazy informer startup. `p` keeps the release's filtered workload-Pods shortcut · `h` history (16b's rail idiom) · `v` values in the YAML viewer, read-only. Rollback inherits 8b friction. **No install/upgrade-from-repo — deliberately out of scope (CI's job); detecting that an upgrade exists is not performing one.** Keybar pill `HELM`.

### 19a — Cluster overview (`g "ov"`)
- Cluster-scoped (namespace drops from breadcrumb). Strip: top-line trouble counts + `v1.30.2 · 5 nodes · 125 pods · 6 namespaces`.
- **A routing layer, not a dashboard** — two-column body, every line a selectable row whose `↵` lands on an existing screen (TROUBLE/CHANGES via 12a/12b's goto machinery, pre-filled — one `esc` back returns to this overview): CAPACITY (cpu/mem/pods bars, same bar idiom; cpu/mem sum only the nodes that report usage, with a dim `cpu / mem — 4/5 nodes reporting` line when some don't) + NODES (pressure/cordoned first, `+ 3 ready` collapse) │ TROUBLE (cluster-wide unhealthy-first aggregation, then 18a's outdated Helm releases last — a chart behind its repo is the least urgent thing in the panel, and `↵` on one lands in the Helm list rather than the pods table; empty = `nothing unhealthy · 125 pods running` in green) + RECENT CHANGES (timeline's rollout feed, cluster-wide, 30m).
- `↹` next panel · `t` timeline · `e` events. **Not the start screen** — pods table (2a) remains the resting state. Keybar pill `OVERVIEW`.

### 20a — Bulk operations (marked set)
- Works in any list. `space` marks the cursor row and advances; `*` marks everything the current filter matches (**filter-then-mark is the bulk grammar** — no range-mark chord). `esc` clears marks before it walks back a level.
- **Mark ≠ selection**: cursor keeps the purple bar + `#1d1633`; marked rows get `▪` (purple) in a leading cell + quieter `#14101f` tint. The mark column exists only while ≥1 row is marked (zero chrome otherwise, 13d's rule). Strip's first slot becomes `▪ 3 marked`; mode pill shows the count (`3 MARKED`).
- Set-applicable verbs act on the set and the keybar says so (`D delete 3 · y/N`, key red); per-row verbs (logs, exec, `↵`) still follow the cursor. Bulk-capability is declared per-verb in the command table.
- `will run` line lists every name: `kubectl delete pod a b c -n <ns>`. Delete follows 8b: inline y/N non-prod; **PROD modal becomes type-the-count** (`type 3 to confirm`) and lists every object. A marked set of Namespaces, CRDs or Nodes gets the type-the-count modal even outside PROD — a set has no one name to type, and the count is exactly the fact a `*`-marked wipe gets wrong.
- Marks are per-view and drop on kind/namespace switch.

### 21a — Secret decode (inside the YAML view)
- Not a new screen — 8a grows secret semantics when the object is a Secret. **Masked by default**: `data` values render `•••••••• · base64 · 41 B` (never raw base64). Masking is structural, never a regex over rendered lines: the object is parsed, every `data`/`stringData` value is replaced before it is marshalled for display (so a key YAML quotes — `"true"`, `"1"`, `on` — is masked like any other, and `/` search can only ever hit masked text), and `kubectl.kubernetes.io/last-applied-configuration` — which embeds the whole manifest, plaintext `stringData` included — renders `•••••••• · contains secret data · N B`. A Secret that can't be parsed shows nothing of its body. Strip: `Secret · Opaque · 4 keys · 1 revealed` + `decoded in memory only — never logged, never on disk`.
- `x` reveals/masks the cursor key in place — plaintext in the string color + a bordered `revealed` tag; `X` reveals all behind an inline y/N. **Leaving the view re-masks everything** — reveal state never persists.
- `y` copies the decoded value of the cursor key (the only plaintext export); `Y` full-YAML copy keeps values base64 (`stringData` folded into `data` as base64, last-applied-configuration dropped). Multiline values expand to an indented block with the fold idiom. Keybar pill `SECRET`.

### 22a — RBAC who-can (registry kind, `g "who"`; `w` from a 403 card)
- **A query, not a browser**: the summary strip holds the question — `who can list secrets in nva-stage` — with `v` verb · `K` resource · `n` namespace opening the palette shell to change each slot (`K`, not `k` — this screen's own `k`/`↑` already means move-up, so a lowercase intercept would have permanently shadowed movement here). With no namespace (opened from an all-namespaces browse) the question reads `◎ all namespaces · cluster-wide grants only`: a RoleBinding grants one namespace, not all, so only ClusterRoleBindings are counted and the strip says so.
- Columns: glyph · SUBJECT · KIND · VIA (`clusterrole/admin ← rb/admins`, ellipsized) · SCOPE (`namespace` dim / `cluster` blue). Resolution walks (Cluster)RoleBindings → (Cluster)Roles **from the watch cache — no server round-trip, works read-only**; wildcards and aggregated ClusterRoles resolve to the effective rule in VIA.
- **Entry from 4b**: the 403 card gains `w who-can`, arriving with the failed verb+resource pre-filled and the current user pinned as a red `✕` row whose VIA explains the closest miss (`role/viewer grants get, list on pods — not secrets`).
- **Who "you" are comes from the server, once.** The pinned identity is the username and groups of one `SelfSubjectReview` (`authentication.k8s.io/v1`, `v1beta1` when v1 isn't served) taken at connect and on context switch and cached — not issued per query, so resolution stays cache-only. The review's groups already carry `system:authenticated` and the service-account groups, so grants to them count. When no review answered (Forbidden, a server without the API, any error) kute falls back to the kubeconfig identity: a client cert's CN and O= groups, else the AuthInfo entry name — and since that name (`arn:aws:eks:…`, `gke_proj_zone_c`) is never a real RBAC subject, an ungranted fallback row renders a neutral `–` with VIA `identity unknown — <name> is the kubeconfig user entry, not the authenticated user`, never a red `✕`.
- `same as` strip shows the equivalent `kubectl auth can-i` (10a's idiom). `↵` opens the binding's YAML — the answer is always inspectable. Keybar pill `WHO CAN`.

### 23a — Ingress routing table (`↵` on an ingress)
- **Not a describe page** — one row per host+path → `service:port`, the join raw YAML makes you do in your head. Backends resolve live from the watch: green ● service exists + ready endpoints; red ✕ `service not found` (inline, never a tooltip); yellow ▲ `0 ready`, or `no such port` when the Service exists but declares no port by that number or name. A pod counts as ready by its `Ready` condition (readiness gates included), never while terminating.
- The ingress **list** earns its keep first: NAME · CLASS · HOSTS · TLS (●/–) · BACKENDS (`3 ok · 1 broken`) · AGE. Strip counts unhealthy-first.
- TLS column shows cert expiry from the referenced secret (yellow <30d, red expired); a strip above the keybar names each secret — `↵` there jumps to it (21a's secret semantics apply).
- `↵` on a route → backend Service (12a/12b's goto machinery, pre-filled — one `esc` back returns to this routing table); `y` copies the full URL. Keybar pill `ROUTES`.

### 23b — HTTPRoute / Gateway API routing table
- Gateway API splits routing across **two objects owned by different people** (Gateway = infra, HTTPRoute = app team, joined by parentRefs). Kute resolves the join both ways: the route's parent strip shows `gw/public › https:443 · ✓ accepted` (from `status.parents`); `p` opens the Gateway (same pre-filled goto jump, one `esc` back).

### 24a — Set image / set tag (`i` on a workload row)
- Available on Deployment, StatefulSet, DaemonSet, and CronJob rows. CronJob edits update `spec.jobTemplate`: running Jobs are unaffected and only future Jobs use the new image.
- Same inline tier as scale (17b) — no modal. Panel opens under the row (bg `#101018`, border `#3b3b58`); container tabs across the top (`↹` switches container). Conventional init containers are editable and labeled `init`; native sidecars are editable and labeled `sidecar` while still targeting their `initContainers` API entry.
- **Tag-first editing:** the `image ›` field pre-fills the current ref with the cursor on the tag, repo prefix dim — the 95% case is "bump the tag." `ctrl+e` unlocks the full ref for the rename case. One verb, two depths, no separate "set tag" screen.
- **History from the watch cache, never a registry call:** a TAG · SEEN · FROM table lists this workload's own ReplicaSet revision history (rollback targets, labeled by revision) plus the same image tag seen on other workloads/namespaces (`3.4.2 · seen 40m ago · nva-prod` — the "promote what prod runs" case).
- Re-entering the current tag flips the strip to `same image — apply is a no-op` and `↵` does nothing; rollout-capable workloads additionally suggest rollout restart.
- `will run` line: `kubectl set image deploy/nva-worker worker=registry.nva.dev/nva-worker:3.4.2 -n nva-stage`, right-aligned `applying rolls out 4 pods`. CronJobs instead show `future jobs only · running jobs unaffected`. Multi-container workloads cycle with `↹`; the will-run line always names the container.
- Keys: `↵ apply · ↑↓ pick from history · ↹ container · ctrl+e full ref · esc cancel`; rollout-capable workloads point to 9a, while CronJobs repeat the future-Jobs consequence. PROD contexts get the inline y/N on apply, per 8b's tiering. Keybar pill `SET IMAGE`.

### 25a — Resources — set limits next to live usage (`r` on a workload)
- **Case keeps the two workload actions distinct:** lowercase `r` opens the resources editor on Deployment/StatefulSet/DaemonSet rows; uppercase `R` remains Deployment rollout-restart with its inline `y/N` confirmation.
- The fix for the OOMKill diagnosed in 5a. Strip under the header: container tabs, `usage: sampled when opened` (one namespace-scoped container-metrics read when the panel opens, carried across post-apply refreshes — not the list's metrics poll), right-aligned failure callout (`✕ OOMKilled 4m ago at the current limit`).
- Table: FIELD · CURRENT · NEW · P95 USAGE, rows for cpu/mem request and limit. Each field's usage renders as a mini bar sourced from that read — the mem-limit row shows the bar pinned at capacity with the OOMKill context, so the new value is a decision, not a guess. No metrics → USAGE column reads `metrics unavailable` dim, editor still works.
- Typing replaces the selected field's value; `+/−` nudges by unit steps (64Mi / 50m). Values parse as k8s quantities — an invalid quantity underlines red inline and blocks `↵`, never a modal (same inline-error idiom as 17a).
- `u` unsets a field (explicit removal, since "no limit" is a real and dangerous state) — the NEW cell then renders `— none` in yellow.
- Validation: request > limit blocks inline before apply; namespace LimitRange/ResourceQuota violations surface as the server's verbatim dry-run message, same idiom as 17a. Only changed fields go into the command.
- `will run` line: `kubectl set resources deploy/nva-worker -c worker --limits=memory=768Mi -n nva-stage`.
- **Same confirm → execute → refresh → show result → remain on screen contract as 26a:** `↵` never closes the editor — all four fields (cpu/mem request/limit) re-fetch from the live container spec afterward (CURRENT and its USAGE bar refresh; NEW resets to match, since nothing's pending anymore), the will-run strip becomes an inline result (`applied cpu.limit=768m, mem.limit=768Mi` — only the fields that changed; an unset one reads `<field>=unset`), and the field you were on stays selected, same container tab. A rejected apply (distinct from the LimitRange/ResourceQuota dry-run check above, which already catches most of these before you ever get here) leaves the typed NEW values exactly as entered with the server's error shown in place of the command preview; `esc` is what actually leaves.
- Keys: `↵ apply changed fields · ↑↓ field · +/− nudge (64Mi / 50m) · ↹ container · u unset field · esc cancel`. Keybar pill `RESOURCES`.

### 26a — Labels & annotations editor (`m` on any object, CRDs included)
- Two grids, LABELS · N then ANNOTATIONS · N, same key=/value/right-note column shape.
- **Hosted from the list (2a) and from every object detail screen** (5a pod, 11b node, 14d CRD, 36e CronJob): browse freezes the selected row above the panel; a detail screen freezes its own title line the same way. The panel is also the only place labels and annotations appear at all — 5a's resting view dropped its LABELS sidebar when the metapanel landed; `m` shows both in full, with `y` copying `key=value`. The shared implementation lives in `internal/tui/metapanel`; per the Global-verb rule `m` is taught once in the `?` overlay's RESOURCE column, never listed per-screen in a closed-panel keybar.
- **Joins render before you touch anything:** a label a Service selector matches carries an inline yellow `⚠ selector · svc/nva-worker`; editing that key requires the inline y/N even though metadata edits are otherwise reversible, and the confirm names the blast radius (`detaches 4 pods from svc/nva-worker`). Deployment selector labels are immutable server-side — kute says so up front instead of letting the apply bounce off the API server.
- Controller-managed annotations (`deployment.kubernetes.io/revision`, `kubectl.kubernetes.io/*`) render read-only dim. On a Secret, last-applied-configuration renders 21a's `•••••••• · contains secret data · N B` and `y` copies nothing from it. Helm-owned metadata stays editable but carries a note that the next `helm upgrade` may revert it.
- Add is one row, not a form: `a`/`insert` opens `key=` targeting whichever grid (LABELS/ANNOTATIONS) currently has focus — `tab`/`shift+tab` switches focus between the two grids — with completion from keys already used elsewhere in the namespace, `↹`/`⇧↹` jumps between key and value.
- Remove: `D` on a key + inline y/N (reversible, no type-the-name modal — per 8b's tiering).
- `will run` line, exact per verb: `kubectl label deploy/nva-worker env=staging --overwrite -n nva-stage` (`--overwrite` only appears when overwriting) / `kubectl annotate` equivalent.
- **The panel stays open through a confirm, not the generic table-with-overlay.** Unlike 8b's own delete confirm — which closes whatever was showing and drops a plain y/N over the bare table — a join-locked edit or a removal's inline y/N renders *inside the still-open editor*: the row under confirmation shows its about-to-apply state (`was nva-worker · nva-worker2` for an edit, a red `remove · y/N` note for a removal) and the panel's own will-run strip prints the exact command (plus the `detaches N pods from svc/X` warning for a join, ahead of the command) — the keybar's own note stays to the short join-warning form alone, since duplicating the full line there routinely overruns its width and gets silently dropped. Cancelling (`n`/`esc`) reverts an in-flight edit's buffer and returns to navigation without closing the panel.
- **The panel never closes on its own account, success or failure — this is a context-preserving inspector/editor, not a one-shot form.** Every commit (a plain apply, a confirmed join-edit, an add, a removal) follows the same contract: confirm → execute → refresh → show result → remain on screen.
  - **Refresh, don't patch locally.** On success the object is re-fetched and the grid rebuilt from the real, current labels/annotations — never the locally-typed value left standing in — so joins, the immutable-selector set, controller-managed annotations, and the Helm-owned note are all recomputed fresh (a value can be normalized or rejected-and-defaulted server-side; the panel always shows what actually landed).
  - **Inline result, not a toast.** The will-run strip becomes the result line: `updated env=staging` / `added tier=gold` / `removed kute.dev/owner` in green — cleared the moment you do anything else in navigation mode, since it only ever answers "what just happened."
  - **Focus follows the change.** The just-touched row stays selected after refresh (matched by key); after a removal, focus lands on the nearest remaining row in the same grid (or nothing, if it emptied out — the `+ a add` hint is still right there).
  - **Failure keeps you mid-edit.** A rejected apply never refetches or discards anything: an edit re-opens editing mode with the exact attempted value still in the buffer, an add re-opens the add row with both fields intact, and the will-run strip shows the server's own error in place of the command preview — fix it and retry, or `esc` out.
  - Only `esc` (navigation mode) or the normal back gesture ever leaves the screen explicitly.
- **Context-sensitive input, not globally reserved keys:** navigation and editing are distinct modes so a typed value never collides with a shortcut. Navigation: `↑↓`/`j`/`k` move within the focused grid, `tab`/`shift+tab` switches grid focus, `↵` opens the selected value for editing, `a`/`insert` adds a key to the focused grid, `D` removes the selected key (+ inline y/N), `y` copies `key=value`, `esc` closes the panel. Editing (entered via `↵`): every printable character — including `a`, `A`, `y` — inserts literally; `↵` saves, `esc` cancels back to navigation without closing the panel, `↹`/`⇧↹` (add-row only) jumps between key and value. Keybar pill `META`, `CONFIRM` while a join/removal y/N is showing.

### 27a — ConfigMap value edit (`↵` on a key, inside a ConfigMap's Data view)
- A value-edit, not a YAML session. Strip under the header names every consumer from the watch (`deploy/nva-worker ↗ env`, `deploy/nva-gateway ↗ volume`), right-aligned `pods don't reload configmaps on their own`. Jobs, CronJobs and bare Pods (no controller) that reference it follow in `TextFaint` after one `not restartable:` marker — read only from caches already running, so opening a ConfigMap never starts the Job or CronJob informer — and `ctrl+r` leaves them alone, its confirm saying so (`restart 2 consumers · 1 not restartable`).
- Table: KEY · VALUE · SIZE. Short values edit in place (prior value stays visible as `was info ·` while typing). Multi-line keys show a folded summary (`▸ 48 lines · e opens the buffer editor`) — `e` opens a multi-line buffer editor scoped to just that value (apply key is `alt+a`, not 17a's `ctrl+s` — `ctrl+s` is the terminal XOFF key in some environments, so this screen's own buffer editor moved off it to `alt+a`, which avoids terminal flow-control keys). `binaryData` keys are listed too, read-only (`binary · read-only`, real SIZE) — their bytes are never shown, `↵`/`D` on one refuse with an inline note pointing at `E`, and adding a key of the same name is refused before it reaches the server.
- Two apply depths from the same row: `↵` applies without restarting anything (kute never restarts consumers on its own); `ctrl+r` chains the apply with `kubectl rollout restart` for every consuming workload and prints every command it runs. Restarting every consumer is never less friction than restarting one (§9a): `ctrl+r` asks an inline `y/N` outside PROD (the row reads `confirm to update + restart 2 consumers · y/N`, the will-run strip lists the patch and every restart) and opens the type-the-name modal in PROD, typing the ConfigMap's own name, with the consumers it restarts and every command listed. `esc` from either confirm goes back to the buffer with the typed value intact. With no consumers it restarts nothing, so it is the plain apply and gets the apply's friction.
- Conflict handling: every patch (edit, add, remove, and the `ctrl+r` apply that precedes any restart) carries the ConfigMap's resourceVersion as observed when the buffer opened, as a merge-patch precondition. A concurrent change is a 409, never a silent last-write-wins: the typed buffer stays open, the result line says `nva-config changed on the server since you opened it — reloaded · ↵ again applies your edit to the latest version`, the ConfigMap reloads, and no consumer restarts. Applying again goes over the reloaded version; `esc` discards to see what changed. No dry-run and no diff/rebase banner — those stay 17a's.
- `will run` line: `kubectl patch cm/nva-config --type merge -p '{"data":{"LOG_LEVEL":"debug"}}' -n nva-stage`.
- **Same confirm → execute → refresh → show result → remain on screen contract as 26a:** `↵`/`ctrl+r` never close the editor — the table re-fetches from the ConfigMap afterward (VALUE/SIZE refresh, a multi-line key's folded summary line count too), the will-run strip becomes an inline result (`updated LOG_LEVEL=debug`, or `updated LOG_LEVEL=debug · restarted 2 consumers` for `ctrl+r`), and the row stays selected. A rejected apply (including the resourceVersion conflict above, which also reloads) leaves the typed value intact with the server's error shown in place of the command preview; `esc` is what actually leaves.
- Keys: `↵ apply · ctrl+r apply + rollout restart consumers · e buffer editor (multi-line) · esc discard`. Keybar pill `EDIT VALUE`. `a` add key uses the same line-insert gesture as 27b.

### 27b — Secret Data view: add a key, decode-then-edit an existing one (`internal/tui/tasks/secretdata`)
- Decode/reveal semantics inherited from 21a. Strip: `Opaque · 3 keys → 4`, right `values decode in memory only · re-masked on exit`. Existing rows stay masked (`••••••••••••••••`) in navigation — adding a key never reveals its neighbors.
- `a` appends a highlighted `+` row: type the key name, `↹` to the value, which is visible while typing (with an inline `ctrl+x re-mask` hint, a chorded key so plain `x` stays typeable in both the key and value buffers) and shows size as `new`.
- `↵` on an existing row is a decode-then-edit, not a blind rewrite: it decodes that key's real value and opens it pre-filled in the same visible-while-typing buffer the add row uses (`ctrl+x` masks/reveals it there too) — the key itself isn't editable this way, only its value. `↵` on an unchanged value is a no-op that just exits editing. A value the single-line buffer can't hold verbatim (multi-line — a PEM, an SSH key — or binary) never opens there: `↵` refuses with an inline note naming the key (`tls.crt is multi-line or binary · can't edit it here — use E on the Secrets list`), since the buffer would start already flattened and a no-op `↵ ↵` would write the corruption back. 26a refuses multi-line annotation values the same way. This is a deliberate departure from 27a/26a's own "same surface, separate screen" framing: Secret's own value-edit lives here, not on a distinct 27a-style surface, since it's the same masked-grid screen either way.
- The `will run` line itself masks the value (`"SMTP_PASSWORD":"••••••"`) for both add and edit — copyable documentation must never leak the secret into scrollback or a shared screen. The real patch sends the value via `stringData`; kute does the base64, not the user. **The whole will-run band (rule and line both) is omitted entirely, not shown as a static "no changes" placeholder, whenever there's genuinely nothing to preview** — plain idle navigation, or an edit sitting unchanged from its decoded original; it reappears the moment there's a real add/edit/removal command (or its confirm, or the last result/error) to show.
- Plaintext exists only in process memory: `ctrl+x` re-masks the input/edit row, `esc` cancels without applying (zeroing the add row's buffer; reverting an edit to its original decoded value), nothing is logged or persisted. `ctrl+v` paste is never echoed to scrollback.
- PROD contexts add the inline y/N on apply for both a new key and an edited one; removing a key keeps the y/N too (recoverable only if the old value exists elsewhere — the prompt says so), regardless of PROD.
- **Same confirm → execute → refresh → show result → remain on screen contract as 26a — with the value never shown either way:** applying never closes the screen — the grid re-fetches from the Secret afterward (masked rows stay masked, focus follows the touched key), and the will-run strip becomes an inline result naming the key alone (`added SMTP_PASSWORD` / `updated SMTP_PASSWORD` / `removed SMTP_PASSWORD` — never `=value`, success or not, per this screen's own no-leak rule above). A rejected apply leaves the input/edit row's typed value exactly as entered (still revealed/masked per its own state) with the server's error shown; `esc` is what actually leaves. Every patch carries the Secret's resourceVersion as observed when the buffer opened (a removal: as last loaded), so a concurrent change is a 409 rather than a silent overwrite — handled exactly as 27a's conflict (buffer kept, `changed on the server since you opened it — reloaded`, `↵` again applies over the latest version), naming the object, never a value.
- Keys: `↵ apply/edit · ctrl+x re-mask · ctrl+v paste (never echoed) · esc discard/cancel`, plus `D` removal on an existing row. Keybar pill `ADD KEY` while adding, `EDIT VALUE` while editing.

### 28a — Update chip (ambient, status bar)
- Zero chrome when no update is pending (13d's rule). With one available, a quiet chip renders left of the connection dot: `↑ 0.2.1` in yellow — same "worth knowing, not urgent" hue as other passive facts; no banner, no flash, nothing steals focus mid-incident. The keybar's right slot names the key while live: `U 0.2.1 available — what's new`.

### 30a — Flux kinds (registry entries, `g "kust"` · `g "flux"`)
- Shared list skeleton. Columns: glyph · NAME · READY · REVISION · SOURCE · RECONCILED · AGE. Strip: `● 12 ready · ◌ 2 reconciling · ✕ 1 stalled · ‖ 3 suspended` + the plain count. Keybar pill = the kind's own short name.
- **Why Flux departs from "CRD support is data, not code."** The generic 14a descriptor answers one question — "does this object's `Ready` condition say True?" — and for Flux that answer is wrong more often than right. `Ready=False, reason=Progressing` is an object working correctly; a suspended object's `Ready` is frozen at whatever it said before an operator stopped reconciliation, so reporting it is reporting a fact that has stopped being true. A generic list renders a healthy GitOps cluster as a column of red. The exception is narrow and precedented: §23b gave HTTPRoute a bespoke ATTACHED column for exactly the same reason ("its health question isn't 'is it Ready'"). Data-not-code holds for the *long tail* — the operator CRD kute has never heard of. Flux is not that: it is a fixed, versioned set of five API groups whose status vocabulary is documented and identical on every cluster.
- **Recognition is by API group, never by kind name.** `helm.toolkit.fluxcd.io/HelmRelease` shares its bare Kind with §18a's Helm-3 release kind, and the registry is keyed on the Kind alone — so before this, a Flux cluster's discovered descriptor silently *replaced* the Helm Releases list (which then rendered NAME + AGE only) while Flux's own HelmReleases never appeared at all. Flux's is registered under a substituted key; only the registry key changes, never the GVR the informer watches, the `involvedObject.kind` events are matched against, or the resource name a printed kubectl command uses. **Matching a discovered kind on its bare name is the bug this section exists to prevent, not a pattern to copy.**
- **Status precedence, highest first: suspended → stalled → ready → reconciling → not-ready → unknown → pending.** Suspended (`‖`) outranks everything for the frozen-conditions reason above. `Stalled=True` is terminal failure (`✕`). `Reconciling=True` alongside `Ready=False` or `Ready=Unknown` is *normal progress* (`◌`, warn) — calling it a failure is the single most common way a GitOps dashboard cries wolf. Nothing requires `Reconciling` or `Stalled` to be present: on a settled cluster the only condition is `Ready`, so the table degrades to the plain Ready read rather than to "unknown". No new status glyphs beyond `‖`.
- **Suspended is amber and stays on screen, not gray and folded away.** Suspended is the Neutral class, which for every other kind means finished-and-uninteresting (a Completed pod) and correctly sinks to the bottom. A paused Kustomization is the opposite: it is the object silently drifting from git, so it sorts *above* healthy rows and is exempt from the healthy-tail fold. Suspended is a state, not a footnote.
- **The condition message renders verbatim, under its row.** Every Flux CRD declares exactly `Ready`, `Status` and `Age` (sources add `URL`), where the declared `Status` column *is* the Ready condition's message — prose like `health check failed after 2m0s: Deployment/nebula-stage/nebula-worker status: 'InProgress'`, which a table cell can only ellipsize into uselessness. It becomes a full-width continuation line under the row instead: muted, never selectable, never paraphrased. A healthy row gets none (its message only repeats the REVISION cell), and neither does a suspended one (the READY cell already says the word).
- REVISION and SOURCE are derived — Flux declares neither, and §14a's "never guesses a column that isn't there" governs the *generic* descriptor, not a curated kind (§18a's Helm columns and §23b's ATTACHED are the same licence). REVISION collapses `main@sha1:efd398be…` to `main@efd398b`; a source's own artifact revision can be a bare 71-character digest, which shortens the same way. SOURCE reads `git/nebula-config`, and `–` on a source kind, which *is* the source.
- **Unhealthy first, healthy tail folded** — `+ 3 ready · ↹ expand`, the same idiom §6b uses per namespace, here on a single-namespace list.
- **Two verbs, and the boundary they stop at.** `s` suspends/resumes (`spec.suspend`); `r` reconciles (a fresh `reconcile.fluxcd.io/requestedAt` stamp). Both are plain API writes: **no `flux` binary is invoked on any path** — a deliberate departure from §18a's rollback, which does shell out to `helm`, since neither of these needs anything that did. Both are TierNone for cordon's reason: reversible and immediate. `o` jumps to the source. **Installing, bootstrapping and committing to git are out of scope** — the same boundary §18a draws with "detecting that an upgrade exists is not performing one": pausing a reconciliation and asking for one now are operations on cluster state kute can already see, whereas `flux bootstrap` writes to a Git repository, which is CI's job.
- **`r` keeps a bare letter against the rule that moved `rollout restart` off it.** That verb was rebound because a single unmodified key fired an unconfirmed pod restart across a whole Deployment with zero friction. Reconcile is not that class of action: it asks for the reconciliation Flux would have run on its own interval anyway, so the worst case of a mistaken press is that a sync happens early. `r` is also how `flux reconcile` is spelled. The exemption does not generalize to a verb that changes state the controller wasn't already going to make.
- **The will-run line names the `kubectl patch`/`kubectl annotate` kute actually issues**, not the `flux suspend`/`flux reconcile` it is equivalent to — §27a's rule that the line names the command that *executes* outranks naming the one a user would recognise faster. The equivalence is documented here and nowhere in the UI.
- Group **Flux** (`⇅`), appended only when discovery finds one of the five Flux API groups, and mutually exclusive with **Custom Resources** — a kind is in exactly one group. Detail is 14d, unchanged; only the title chip's word comes from the list's own derivation rather than a raw Ready condition, so no per-CRD knowledge leaks into that screen. CONDITIONS stays verbatim there, `Stalled: True` rendered green included, per 14d.

### 31a — Kustomization detail (`↵` from 30a)
- Failure card first, chain second, inventory third — 5a's promotion rule. `RECONCILE FAILED · 4m ago · retry in 3m 12s`, the condition message verbatim, then the resolved drill-through: kute follows the failing health check to the Deployment to its pod and prints the real reason (`exit 137, OOMKilled`) inside the Flux card. Zero digs.
- Chain grid: `source` (sourceRef + path + interval), `source revision`, `applied revision`, `depends on` (amber when a dependency is suspended — the second most common "why won't it reconcile").
- **`in sync — applied, failing health checks`** distinguishes the two failure families: drift (not applied) versus unhealthy (applied, workload sick). One line kills the most common Flux misdiagnosis.
- INVENTORY lists what the Kustomization manages, from its own `status.inventory`, unhealthy first with the healthy tail folded; `↵` opens the object. A HelmRelease publishes no inventory (it delegates to Helm's own storage) and says so rather than showing an empty list.
- **The commit subject and author are not on the cluster.** `status.artifact` carries only the revision, digest, size and timestamps, and the fetched tarball excludes `.git`. The subject is recoverable *only* from source-controller's own Events (`stored artifact for commit '<subject>'`), which expire, so it is cached per context when seen and degrades to the bare SHA otherwise. **Drift is a boolean, never a commit count** — `N commits ahead` needs `git log`, and kute reads no git remote and holds no tokens.
- Keys: `esc · ↵ open object · r reconcile · s suspend · o source`. Keybar pill `KUSTOMIZE`.

### 32a — Incident timeline learns git (extends 16a/16b)
- No new screen, one new entry source. A revision-applied entry renders `◆` in accent purple — the only purple marker in the feed — and reading top-down gives the causal chain: commit → rollout → OOM → backoff. On a GitOps cluster the timeline's question ("what changed?") is answered by a commit.
- **No new machinery**: Flux controllers already emit these as ordinary Kubernetes Events, so they arrive through the read 9b/16a already do. The revision itself needs no parsing — a Kustomization's event carries it as an event *annotation* (`kustomize.toolkit.fluxcd.io/revision`); only the commit subject comes from message prose, and only when the source-controller event is still within its TTL or was cached earlier.
- Routine no-change reconciles collapse into the existing quiet line — 22 identical events would otherwise bury the one revision that mattered. `v` copies the revision, the thing you paste into `git show` or an incident channel.
- **Zero chrome on a non-Flux cluster**: no Flux, no `◆` rows, nothing added.

### 34a — Argo CD syncs join the timeline (extends 32a)
- No new screen, one more entry source: Argo's `OperationCompleted` events (argocd-application-controller's own signal that a sync just finished) become their own `◆` rows in the exact same merged feed §32a's Flux revision rows already render into — "one ◆ marker, two GitOps engines." A cluster running both (common mid-migration) gets one causal stream, not two: `sync → rollout → crashloop` reads top-down as the incident story regardless of which controller applied the commit.
- **The fields come from the object, not the event.** Unlike a Flux reconcile event — which stamps the revision it just applied directly on its own event annotation — Argo's `OperationCompleted` event carries neither the revision nor who/what triggered it. Both are read off the Application's own `status.operationState` (`operation.sync.revision`/`syncResult.revision` for the ref+SHA, `initiatedBy` for the initiator) once the event names which Application finished.
- **No commit subject, ever.** §32a's subject comes from source-controller's own `stored artifact for commit '<subject>'` event prose — Argo emits no analogous message, and there is no other on-cluster source for one. A sync row is `Sync applied · application/nva-billing · main@e41b90c · ci-bot`, revision and initiator only; never a fabricated or borrowed subject.
- **"auto-sync" vs a name matters at 2am** — was this a human or the machine? Argo's own `operationState.initiatedBy` distinguishes an automated sync from a named one, and kute prints whichever applies rather than always crediting a person. A sync with no recorded initiator names nobody, never `auto-sync`; one started from §33a's `S` carries kute's own `initiatedBy.username`, so it reads as the person who pressed it (or `kute`).
- `v` copies the revision here too, same as on a §32a row — the thing you paste into `git show` or an incident channel.
- **Zero chrome on a non-Argo cluster**: no Argo, no sync rows, nothing added.

### 33a — Argo CD Applications list (registry entries, curated exception — extends §30a)
- **One tier shallower than Flux, on purpose.** Flux earned a bespoke join view (§30b) because it has no UI of its own. Argo CD has a good dashboard, so kute doesn't rebuild it: this is the §30a/§32a treatment only — a curated registry entry for `Application`, the same timeline enrichment (§34a), honest kubectl-equivalent verbs. No 30b-style tree for Argo, by design — the value kute adds is the 2am terminal moment: see the degraded app, jump to its broken workload, read the exit code, no browser, no SSO.
- Shared list skeleton. Columns: glyph · NAME · SYNC · HEALTH · REVISION · SYNCED · AGE. Keybar pill `ARGOAPP`. A multi-source Application (`spec.sources`) has no one ref, so its REVISION reads `N sources` and its `S` patch carries no `revision` — Argo then syncs each source to its own `targetRevision`.
- **Sync and health are independent axes, so they get independent columns.** `Synced`+`Degraded` (git is right, the workload is sick) and `OutOfSync`+`Healthy` (drift, nothing actually broken) are different incidents, and collapsing them into one glyph the way a single condition would (as §30a does for Flux) would lose that distinction. Sort order: `Degraded` → `OutOfSync` → `Progressing` → `Healthy`.
- **Recognition is by API group *and* Kind, never by bare Kind name alone.** `argoproj.io` also serves `AppProject`, which carries no sync/health status at all — the same group-plus-Kind gate §23b's HTTPRoute descriptor uses within Gateway API's own shared group. `AppProject` stays on the generic 14a custom-resource path untouched.
- **The sub-line is the sickest managed resource's own health message, verbatim** — Argo's own `status.resources[]` rollup already names the worst-off object and why (`Deployment/nva-billing-api: container "api" is in CrashLoopBackOff — exit 1, 2m ago`), the same "prose renders as a continuation line, never paraphrased" rule §30a's Ready-condition sub-line follows. Shown only on a Degraded/Missing row — a healthy or merely-drifting app has nothing a table cell hasn't already said.
- **The three verbs, all plain API calls — no `argocd` binary, no SSO.** `r` refreshes (`kubectl annotate application/<name> -n <ns> argocd.argoproj.io/refresh=normal --overwrite`) — TierNone, the same "asks for what the controller would do anyway" reasoning §30a's Flux reconcile gets, since it only asks argocd-application-controller to re-diff early. `S` syncs (`kubectl patch application/<name> --type merge -p '{"operation":{"initiatedBy":{"automated":false,"username":"<you>"},"sync":{"revision":"<rev>"}}}' -n <ns>`) against the app's own already-configured target revision, credited in Argo CD's own `OperationInitiator` shape to `<you>` — the username of the connect-time `SelfSubjectReview` (22a's identity), or `kute` when no review answered, never left blank (which §34a would have to show as nobody) and never `automated` — a real, visible change to what's deployed, so unlike refresh it gets the ordinary TierInline will-run y/N (PROD escalates to the modal), never the delete-grade type-the-name treatment. `prune=true` sync is out of scope for this section; were it added later it would be delete-class (y/N in keybar), the same line §30a draws for its own two verbs. `u` copies the one concession to the dashboard: the deep link built from `argocd-cm`'s own configured `url` key plus the app's namespace/name (`argocd-cm` is looked up in config.yaml's read-only `argoCDNamespace` first when set, then the Application's own namespace, then `argocd`) — for sync waves, app-of-apps graphs and diffs, the right tool already exists, and kute hands over the link instead of imitating it. The will-run line always names the `kubectl` command kute actually issues, never the `argocd` CLI equivalent it matches — §27a's rule.
- `D` delete follows the ordinary 8b tiering, unchanged — no Argo-specific delete behavior.
- Group **Argo CD** (`◎`), appended only when discovery finds the `Application` kind, mutually exclusive with **Custom Resources** — same conditional-append, zero-chrome-otherwise shape §30a's Flux group uses. Detail is 14d, unchanged — there is no bespoke Argo detail screen the way Flux has 31a.

### 30b — Flux tree (`g "flux"`)
- One screen grouped by source: each GitRepository/HelmRepository/OCIRepository/Bucket with the Kustomizations and HelmReleases it drives nested under it, `└─` per child. Columns: glyph · SOURCE / RECONCILER · KIND · REVISION · RECONCILED. Keybar pill `FLUX`.
- **The join is the value.** Flux's failure mode is chain-shaped (source fetches → reconciler applies → workload rolls out) and no kubectl view shows the chain — you reconstruct it by reading two lists and holding each object's `sourceRef` in your head. Same both-ways-join argument §23b makes for Gateway API.
- **A computed view over the registry, not a second implementation of Flux.** Every row's glyph, status class, revision cell and condition sub-line is the kind descriptor's own §30a projection, unchanged — the two screens cannot disagree about an object. All this screen adds is the arrangement. That is also what keeps it inside "kinds are data, not code": 30a remains the registry baseline that lists each kind; 30b is a join on top, the same class of exception as the incident timeline (§16a), which is likewise a computed merge rather than a new kind.
- **Reached only from the goto palette, and only on a Flux cluster.** `g "flux"` — a synthetic corpus entry (like `g "ov"` and `g "who"`) with no descriptor of its own, since there is nothing here to list. A cluster serving no Flux CRDs gets no entry at all: zero chrome, per 30a. The breadcrumb carries no namespace segment because the chain crosses namespaces by design — a Kustomization in one namespace routinely reconciles from a GitRepository in `flux-system`, and scoping to one would misdescribe what is on screen.
- **Drift is a boolean here too — `source ahead`, never `−9`.** The mockup drew a commit delta; counting commits needs `git log` against the remote, which kute never has (see 31a). And the comparison only runs where the two revisions are the *same kind of thing*: a Kustomization records the git revision its GitRepository published, so an inequality is real drift, but a HelmRelease records a **chart version** while its HelmRepository publishes an **index digest**. Those are never equal, so comparing them would brand every healthy Helm chain "source ahead" forever — a confident, always-wrong claim, which is worse than saying nothing. A chart repository's own REVISION cell reads `index · 14m ago` for the same reason: its artifact is the index, whose digest names nothing a human compares.
- **`r`'s scope follows the cursor.** On a source row it reconciles the source; on a reconciler row it reconciles *with-source* — the source is annotated first, because asking a reconciler to sync against a stale artifact just re-applies what it already has. One key, two commands, and the will-run line shows both joined by `&&` rather than hiding the difference. A reconciler under a missing source reconciles alone, and a source annotate that fails (no RBAC in its namespace) still lets the reconciler's own go ahead, with the result naming the half that failed. `s` suspends/resumes exactly as in 30a. `↵` opens 31a's inventory on a reconciler; on a source — which publishes an artifact, not a set of applied objects — it opens 14d's generic detail instead, since the inventory screen has no question to answer about one. **Both push, so one `esc` comes back** — the same one-push-one-pop contract a feed like 9b or 16a gives its `↵`. The tree is a place you work *from*, so `o` doesn't navigate at all here: a reconciler's source is its own parent row, already on screen, so `o` moves the cursor to it.
- **Unhealthy chains first; a working chain is one line.** A group folds away only when the source *and* every reconciler under it is healthy, summarised as `+ 2 sources · 5 reconcilers ready · ↹ expand`. A suspended reconciler is deliberately not "healthy" for this purpose — it is the object drifting from git, which is what the screen is read for.
- **A Kustomization says where its objects landed.** A sub-line under each Kustomization with an inventory summarises it by namespace, largest first — `applies 58 objects · gitlab 12 · monitoring 20 · +3 namespaces` — so a push that only added manifests to an existing Kustomization (a new app namespace under `flux-system`, the commonest GitOps change there is) is visible on the tree rather than only in 31a. A Namespace object counts toward the namespace it creates; other cluster-scoped objects count only toward the total. It reads the ids already on the object and nothing else: per-object *health* here would mean listing every kind any inventory names, one informer each, which is 31a's job for one reconciler at a time. A HelmRelease publishes no inventory and gets no such line.
- **A HelmRelease's `spec.chartRef` is a sourceRef too.** An OCIRepository ref nests the release under it; a HelmChart ref is followed one hop to the repository that chart is fetched from, since HelmChart is an artifact, not a source this screen draws — and HelmChart is only listed when some release actually names one.
- **A `sourceRef` that resolves to nothing is a finding, not an omission.** The reconciler still appears, under a heading naming the reference that was looked for (`source not found: helmrepository/bitnami in flux-system`). That heading has no object behind it, so it is never selectable and carries no verbs.

### 36a — CronJobs list (extends 9a — `↵` detail · `ctrl+r` run now · `s` suspend/resume · `S` edit schedule)
- Not a new screen — the shared list skeleton with CronJob's own columns: status glyph · NAME · SCHEDULE · SUSP · ACT · LAST RUN · NEXT. CronJobs **default to name order**, same as every other non-workload kind, but sort like any other screen otherwise: numeric manual-sort keys (2a) pick a column, the same key pressed again flips direction, and the sort arrow renders on the active column — a suspended cronjob is usually suspended *by you, this morning*, so name order is the useful resting state, not a rule that blocks the user from choosing another one.
- **NEXT is computed, not stored**, off the same UI-only clock (`tea.Tick`, once a second, only while a CronJob screen is on screen) that drives the strip's own `clock HH:MM:SS UTC` — never a poll, never `status.lastScheduleTime`. An explicit `spec.timeZone` gets an exact countdown; an unset one is evaluated by the kube-controller-manager process's *own* local timezone, which no interface exposes to Kute, so the row renders `controller local` and `NEXT —` rather than assuming the workstation's zone or UTC.
- **LAST RUN carries the newest *terminal* associated Job's outcome** (✓/✕) — not the currently active one, so an active row can read `2m ago ✓` in LAST RUN while ACT reads `1`, exactly as 36a's mockup shows. Suspended rows render dim with a struck-through NAME, amber `SUSP yes`, and `NEXT —`. **Every failed row expands its own inline reason line beneath itself, always** — the deepest Job condition message, verbatim — the same always-on treatment §30a/§33a's Flux/Argo SubLine already gets, not gated by selection.
- The strip beneath the table carries the selected row's own behavior-changing metadata — concurrency policy, starting deadline, success/failure history limits, timezone, job-template backoff limit — the one job an always-docked side pane would have earned, done in one line instead of a second focus target.
- **`↵` opens CronJob detail (36e) — never a shortcut to Pods.** Every kind in Kute opens its own detail on `↵`; a CronJob is no exception, and doubling as a Pods filter would have made it the one list with two different destinations for the same key. `l` opens logs for the newest useful Pod of the selected row's most recent associated Job — active or terminal, succeeded or failed — with inline feedback when the row has no runs at all or no Pod has been created yet or was already garbage-collected.
- Keys: `↵ detail · ctrl+r run now · s suspend/resume · S schedule · l logs · y yaml · g goto`. Keybar pill `CRONJOBS`.

### 36b — `ctrl+r` run now (reversible tier, staged)
- `ctrl+r` — not bare `r`, which means retry/refresh everywhere else in Kute — stages a manual run in screen state: the selected CronJob, whether an associated Job is currently active, and the exact generated Job name. `↵` executes through the reversible tier, `y` copies the will-run command, `esc` cancels — no inline `y/N`, no modal: the created Job is reversible and deletable, and the schedule itself is untouched.
- **Overlap warning appears only when an active associated Job genuinely exists.** `Forbid`/`Replace` concurrency get warning treatment, `Allow` gets quieter informational treatment; the card names the active Job(s) by name and states plainly that a manual run bypasses `concurrencyPolicy` entirely and that the next scheduled run is unaffected. A complete Job view with no overlap renders zero warning chrome — just the will-run line. When Job data could not be listed, the card says overlap is unknown rather than silently rendering the no-conflict path.
- The will-run band shows the real `kubectl create job … --from=cronjob/…` command plus the exact Kute source/creator/trigger-time annotations applied atomically. The creator is the API server's own answer to who you are — the connect-time `SelfSubjectReview` username (§22a), read when the run is staged — falling back to the kubeconfig user name only when no review answered, and to `kute` when neither is known; 37c's rerun stamps the same creator, and the Jobs list's `manual · you` compares against it. The manual Job is deliberately **ownerless**, so CronJob history garbage collection never deletes it, and is associated back to its source CronJob purely through those annotations — never a fake owner reference or name-prefix match. The generated name is a readable, collision-safe, deterministic `-manual-HHMM` in UTC; the name shown in the preview is the exact name the Job gets.
- On success Kute remains on the list: the created Job appears in history and ACT through the ordinary Job watch event, and logs become available only once the corresponding Pod watch event lands — Kute never assumes a Pod exists immediately.

### 36c — `s` suspend/resume (one key, asymmetric friction)
- One key, both directions — the row's own SUSP column and strike-through already say which way it goes, so a second key would be redundant state to remember. The keybar label flips to `resume` when the cursor/marked row is suspended.
- **Suspend is the dangerous half:** it fails silently and forever, and nobody gets paged for a scheduled run that never started. It costs a keystroke — inline `y/N` outside a PROD context, the type-the-name modal inside one (`config.yaml`'s `prodContexts`, never a name heuristic) — and the card names any currently-active Jobs and states plainly that they are unaffected: suspend only stops *future* scheduling.
- **Resume is reversible and executes on `↵`** with no destructive escalation, the same class cordon already occupies — but it still stages first, the same as run-now, so the preview can show suspended duration, a bounded missed-schedule count, and the next run before commit.
- **Missed-schedule copy is a computed warning, not an absolute claim.** Kubernetes does not always skip a backfill on resume — it can start one immediate Job when eligible missed runs remain, especially when `startingDeadlineSeconds` is unset. Resume renders `N schedules were missed · Kubernetes may start one immediately on resume`, says so explicitly when the deadline makes every missed run ineligible, and caps the count at `100+` rather than an exact, possibly enormous number.
- **Suspend duration is truthful, never guessed.** A Kute-initiated suspend stamps Kute's own timestamp and expected-generation annotations, trusted only while the annotated generation still equals the CronJob's current generation — so an external resume followed by a later external suspend can't reuse a stale timestamp. A CronJob suspended externally (or changed in a way that invalidates the marker) renders `suspended · start unknown` and omits a fabricated skipped-run count.
- Works on a marked set too: `s` suspends or resumes every marked CronJob behind one confirmation (PROD escalates to type-the-count), joining per-row failures and keeping only the failed marks afterward.

### 36d — `S` schedule editor (pushed task, `internal/tui/tasks/cronjobschedule`)
- **Not an inline browse buffer** — a dedicated pushed screen, reached and left the same way every other editor is, with its own breadcrumb segment (`cronjob/report-nightly › Schedule`) and one `esc` back. One field, three kinds of live feedback: a per-field MIN/HOUR/DOM/MONTH/DOW breakdown, a conservative English description, and the next five real timestamps in the selected timezone — the timestamps are the proof, the sentence is a courtesy.
- **WHAT CHANGES diffs the old and new firing sets** over a fixed upcoming one-year window: what stops happening, the annual delta, and whether the next pending occurrence moves — computed asynchronously (keyed to an edit generation, so a stale result from an earlier keystroke is never shown) and labeled `at least`/`truncated` rather than exact if the comparison hits its iteration cap.
- **Timezone is shown always and editable on `tab`, gated by a real capability read, never an inference.** A single cached `Discovery().ServerVersion()` read, taken once at connect/context-switch, backs a tri-state `supported`/`unsupported`/`unknown` capability: Kubernetes 1.27+ is `supported`, below 1.25 is `unsupported`, 1.25–1.26 is `unknown` unless an already-populated `spec.timeZone` on the object is itself direct evidence that this particular object's field works. `unknown`/`unsupported` makes the timezone field read-only rather than fabricating a cluster version or letting a write silently get pruned by an older API server; an already-populated value stays visible regardless.
- **Apply is a reversible `TierNone` patch**, following the same confirm → execute → refresh → show result → remain-on-screen contract every context-preserving editor in Kute follows: it patches schedule and (optional) timezone atomically, carrying the source `resourceVersion` as a precondition so a concurrent external edit surfaces as an explicit conflict — offering reload — rather than a silent overwrite. A successful apply keeps the previous accepted pair and exposes a one-step undo, itself an ordinary reversible mutation through the same registry. `ctrl+y` escapes to the full YAML editor (17a) for anything else on the object (concurrency, deadlines, history limits); returning from it reloads this screen.
- **The PROD-only confirmation the mockup implies is gone.** The dedicated editor is itself the intentionality gate a bare inline browse buffer would have needed one for — schedule apply and undo are `TierNone` in every context, PROD included.
- Keys: `↵ apply · ctrl+t copy · tab timezone · ctrl+y full yaml edit · esc back`, plus `ctrl+z undo` after a successful apply. Keybar pill `SCHEDULE`. Every non-`↵`/`tab`/`esc` key is a control chord because a schedule or timezone buffer always has focus: as bare `y`/`u`, copy and undo ate the letters out of `@daily`, `@hourly`, `0 2 * * sun` and `UTC`.

### 36e — CronJob detail (`↵`, pushed task `internal/tui/tasks/cronjobdetail`)
- Same recipe as pod detail (5a) and node detail (11b): facts grid on top, the diagnosis in the middle, a related-objects table at the bottom, keybar underneath — CronJobs get no bespoke navigation.
- **Facts grid:** suspended, concurrency, deadline, job-template backoff limit, active count, configured history limits, last schedule time, and a best-effort controller/manager link. A filled failure band — the Job's own condition message, plus a representative exit-code/log target when a Pod was actually collected — renders only when retained failure data exists; Kute never implies it retained logs of its own (that is v0.9.0 Job-ledger scope).
- **The JOBS table is the generic Jobs list, scoped to this CronJob's associated Jobs** — same columns, same SOURCE column distinguishing `schedule HH:MM` runs from `manual · ctrl+r` ones, `↵` emitting the shared goto navigation onto the exact selected Job (a bespoke Job attempt-ledger is v0.9.0 scope; for v0.8.0 this pushes the ordinary Jobs list with the row already selected).
- **The heading reads "associated with this cronjob," never "owned by this cronjob."** Manual Jobs are deliberately ownerless (36b) so CronJob history GC can't delete them, and are linked back purely by Kute's own annotations — the table genuinely mixes controller-owned scheduled Jobs and annotated standalone manual ones, so "owned" would misdescribe half of what's listed.
- **Retention wording is honest about what Kubernetes actually kept:** `4 retained · history limits 3 succeeded / 1 failed` — never a fabricated lifetime total like "4 kept of 218 run." Kubernetes exposes retained Jobs and configured history limits, not how many Jobs it has already garbage-collected; a future persisted Job ledger could add an *observed-since* count, but nothing in v0.8.0 invents one.
- **`j`/`k` and arrows move the Jobs table's own row selection; `[`/`]` move between sibling CronJobs**, matching `poddetail`'s own movement contract. This deliberately replaces the mockup's `j/k next cronjob`, which would otherwise collide with selecting a Job for `↵` and with the repository-wide `j/k == ↑↓` invariant.
- Every mutating verb from the list works here unchanged — `ctrl+r`, `s`, `S` — so arriving at detail never means backing out to the list to act. `e` opens object-scoped events, `y` opens the CronJob's own YAML, `esc` pops one stack level.
- Keys: `esc back · j/k jobs · [/] sibling cronjob · ctrl+r run now · s suspend · S schedule · e events · y yaml`. Keybar pill `DETAIL`.

### 37a — Jobs list (extends 9a — `↵` attempts · `l` logs · `R` rerun · `s` suspend/resume)
- Not a new screen — the shared list skeleton with Job's own columns: status glyph · NAME · COMPL · DURATION · FAILED · SOURCE · AGE. Jobs **default to unhealthy-first, then newest** (same rank as every other workload kind, tiebroken by AGE rather than name — a same-rank tie usually means "which one just failed," and newest is the more useful read than alphabetical); numeric manual-sort keys (2a) still pick any column and override the default — pressing SOURCE's own column key clusters the list by source without a dedicated group-by key of its own.
- **COMPL and FAILED are deliberately two columns, not one "status" string.** COMPL is `Status.Succeeded`/`Spec.Completions`; FAILED is `Status.Failed` — a count of failed *pod attempts*, not a Job-level bool. A Job at `0/1` with `3` failed has burned its `backoffLimit`; a Job still `Active` with `1` failed is retrying and probably fine — collapsing the two into one glyph would erase exactly that distinction.
- **DURATION runs live for an active Job** (the same one-second UI clock, `tea.Tick`, that drives CronJob's own NEXT column — never a poll), **freezes at completion, and turns red when it reaches `spec.activeDeadlineSeconds`** — independent of the row's own health color, since a still-`Active` Job can already have crossed its own deadline.
- **SOURCE is resolved from ownerRefs, Helm's own hook annotations, and Kute's manual-run tag**, in that precedence order: `cronjob/<name>` (a real controller owner reference or Kute's own association annotations), `helm/<release> <hook>` (`helm.sh/hook` + the Helm 3 ownership annotation), `manual · <creator>` (Kute's own rerun "create" path, §37c), or `— standalone` when none apply.
- Suspended Jobs (`spec.suspend`, Kubernetes 1.24+) render dim with a struck-through NAME, the identical treatment suspended CronJobs already get.
- **`↵` opens the attempt ledger (37b/37d) — never a shortcut to Pods.** `l` tails the newest pod this Job has created, regardless of state, directly from the list — the common case is "show me why it failed," and that shouldn't cost two hops.
- Keys: `↵ attempts · l logs · R rerun · s suspend · y yaml · D delete`. Keybar pill `JOBS`.

### 37b/37d — Job attempt ledger (`↵`, pushed task `internal/tui/tasks/jobattempts`)
- One screen, two renderings, gated on `spec.completionMode`: a flat attempt table for an ordinary Job, an index-completion list for an `Indexed` one — never two destinations. Same recipe as CronJob detail (36e): a status banner and failure card on top (the diagnosis, promoted first), the attempt data underneath, a spec strip below that.
- **Scope decision (v0.9.0): there is no retained-pod ledger.** The attempt table/index list reflects only pods still in the informer cache — a pod Kubernetes has already garbage-collected simply isn't listed, and FAILED (37a) can legitimately read higher than the number of visible attempts. The Job's own `Reason`/`Message` condition stays the authoritative fallback for the failure card either way, the same "a missing Pod must never erase a valid Job-level failure" rule 36e's own Jobs table already follows. A future retained ledger — capturing exit code and a log tail at the moment a pod terminates, before Kubernetes deletes it — is exactly the kind of addition this screen's data layer (`resources.BuildJobAttempts`) was built to accept without a signature change; nothing in v0.9.0 builds it.
- **The status banner and failure card promote the deepest real message** — the Job's own condition reason/message, an attempt-count-vs-`backoffLimit` reading, and (for a cronjob-sourced Job) the owning CronJob's name — the same "answer why it's broken first" precedent poddetail's termination banner and 36e's own failure band already set. `d` compares the selected attempt against attempt 1 — without a retained log tail, the comparison is exit-code/result only, not a text diff of two tails.
- **The index-completion view (37d) renders as a selectable list, not a 2D box grid** — one row per completion index (status, attempt count, duration), colored the same way the flat table is. The data matches the mockup (per-index status/duration, `f` filters to failed-only, `↵` opens that index's own attempts); the layout is a documented simplification of the visual grid.
- **The spec strip** carries `backoffLimit`, `completions`/`parallelism`, `deadline`, and — when set — a `ttlAfterFinished` countdown in amber ("object deleted in `N`"), the same "this evidence disappears" urgency 36e's own history-limit line carries. An Indexed Job additionally shows an ETA line once enough indexes have finished to be a meaningful sample (never a progress bar, never polled).
- Keys: `↵ logs of this attempt · d diff vs attempt 1 · e events · R rerun · esc back` (Indexed adds `f failed only`). Keybar pill `ATTEMPTS`.

### 37c — `R` rerun (staged create-vs-replace choice)
- Jobs are immutable once created, so "rerun" is honestly one of two things, staged in screen state before either ever reaches a confirm: **create** — clone the Job's own template into a new `<name>-rerun-N` object, the source Job (and 37b's own attempt data) untouched — or **replace** — delete the Job (Background propagation, so the old attempt's pods go with it, as every kute delete does) and, once the old object is actually gone, recreate it under the same name; if it doesn't disappear within a bounded wait, or the create fails, the result says explicitly that the original was deleted and no replacement exists. `↑↓` picks, `↵` commits. Reachable identically from the Jobs list (37a) and from within the attempt ledger (37b/37d).
- **Create is the default, and staging it is itself the confirmation** — the same "stage first, `TierNone` commit" shape run-now already established: no inline `y/N`, no modal. **Replace is the destructive alternative** and staging it does *not* itself confirm anything — committing still routes through the ordinary tiered confirm (inline `y/N` outside PROD, the full type-the-name modal inside one), because it genuinely destroys the original Job's Status, events, and attempt history.
- **An amber diagnostic strip appears only when the prior failure is one Kute can classify** — a deadline kill (`spec.activeDeadlineSeconds`), or every retained attempt sharing the same exit code — never decoration, and never shown at all when nothing about the failure is legible.
- A rerun of a cronjob-owned Job is always a standalone copy: Kute's own CronJob-association annotations are stripped from the clone (never carried over via the cloned annotation map), so it never counts toward that CronJob's history limits or garbage collection, and it reads `manual · <creator>` in SOURCE (37a) rather than a stale `cronjob/x`.
- Keys (staged): `↑↓ create/replace · ↵ commit · esc cancel`. Keybar pill `RERUN`.

### 41a — Exec picker on a shell-less container (the debug fork)
- **No new top-level key.** `x` means "get me a shell near this object"; the object's kind + state decide which kubectl subcommand delivers it — a **shell-provider declaration in the command table** (exec / ephemeral / copy / node), not a new screen. Declared per kind alongside the other verbs.
- The exec picker (10a) already detects shells. A container with none renders its right-hand cell as `no shell` (`Warn`) instead of a shell list, and the panel's explain block reads `no sh or bash in gateway — nothing to exec into` + `debug attaches a shell alongside it, sharing the pod's process namespace`.
- **`↵` follows the cursor and never dead-ends:** on a shell-less row the key label is `↵ debug <container>` (routes to 41b); on a row with a shell it stays `↵ open shell`. Keybar pill stays `EXEC`.
- If **no** container in the pod has a shell, skip this panel and open 41b directly — a picker with nothing to pick is chrome.
- **Capability is checked authoritatively inside DEBUG, before launch:** opening the panel issues one live `SelfSubjectAccessReview` for the current mode (`create pods/ephemeralcontainers` for attach, `create pods` for copy). While it runs, `↵` is unavailable; an explicit denial stays visible in the panel with the server's reason and `w who-can` (22a). The cache-local who-can graph explains RBAC but never decides whether launch is allowed, because another authorizer or an authenticated group absent from token data may change the real answer. A failed/inconclusive review warns and fails open so the launch itself remains the API-server backstop.

### 41b — Debug panel · ephemeral container on a running pod
- Same centered-panel recipe as 10a/13a, ~880px-equivalent wide (the `will run` line must not clip). Header: `⚑ debug › <pod>` + right `pod running · ephemeral container`. Keybar pill `DEBUG`.
- **MODE is two selectable rows, not a form** — `attach ephemeral` (`shares this pod's namespaces · nothing restarts`, tagged `default`) and `copy pod` (`a new pod from this spec · for pods that won't stay up`, key `m`). Pod state picks the default; `m` overrides. Each row states when it applies.
- **Fields edited in place on their row** (13a's local-port idiom), label in `TextFaint`, value bright, hint in `TextGhost`: `image nicolaka/netshoot▎` (`i` edit · recents), `target gateway` (`t` cycle · "shares the process namespace, so its pid is visible"), `profile general` (`p` cycle · netadmin · sysadmin · restricted). Image recents are remembered per context in the existing persisted state — **no image registry, no config file, no wizard**.
- **Profile is shown, never hidden** — `general` default; `sysadmin`/`netadmin` are visible escalations.
- **Warn-tinted caution line** above `will run`: `⚑ becomes part of this pod — an ephemeral container cannot be removed, only outlived`.
- The live access status appears above `will run`, so leaving with `esc` and immediately pressing `x` always reopens this panel; lazy RBAC informer state cannot consume the second key.
- `will run`: `kubectl debug -it <pod> -n <ns> --image=<img> --target=<container> --profile=general`.
- **Friction tier:** irreversible mutation of a live pod earns the panel + the `will run` line, not a modal; PROD contexts add an inline `y/N` in the keybar on `↵`. The red border stays reserved for delete and drain (8b).
- Handoff is exec's: kute suspends, `kubectl debug` owns the tty, exit lands back on the same pod. No embedded terminal.
- Keys: `↵ start · m mode · i image · t target · p profile · esc cancel`.

### 41c — Debug panel · copy mode (the pod won't stay up)
- `x` on a not-running pod (CrashLoopBackOff etc.) opens the panel **directly in copy mode** — exec and ephemeral attach are both impossible. Header right: `✕ CrashLoopBackOff · ↺ 6 · copy mode`.
- **The impossible tier stays listed and dim with its reason** (`attach ephemeral — needs a running container — this one is in backoff`) rather than vanishing; the panel teaches which tool applies when.
- Fields: `copy name <pod>-debug` (edited in place), `container worker` (`t` cycle — image kept, so you debug the real thing), `profile general` (`p` cycle, shared with attach mode), **`entrypoint sh` in `Warn` — "replaces the command — that is what stops the crash loop"** (the whole trick, on a row, not buried in a flag), `processes shared` (`s` toggle).
- Caution line: `⚑ creates a real pod — it counts against quota and it is yours to delete`.
- `will run`: `kubectl debug -it <pod> -n <ns> --copy-to=<pod>-debug --container=worker --profile=general --share-processes -- sh`.
- **Cleanup is named, not silent:** on exit, an inline keybar prompt (never a modal) — pill `CLEAN UP` + `<pod>-debug still running · 4m` + `ctrl+d delete it` (key `BadSoft`) / `esc keep`. The copy also carries a `⚑ debug copy` tag in the pods table for the rest of the session (session registry, same as forwards 13c).
- Copy mode is a create and the result is deletable → 8b's reversible tier: inline `y/N` in PROD, no type-the-name.
- Keys: `↵ create + attach · m mode · t container · p profile · s processes · esc cancel`.

### 41d — Node debug (`x` on a node) · **replaces the legacy `s` node-shell**
- Exec on a node is meaningless, so on Nodes (11a/11b) `x` means `kubectl debug node/…`. Header: `⚑ debug › node/<name>` + right `host namespaces · privileged · ↵ runs as-is`.
- **Removal of `s`:** the legacy NodeShell key ran a privileged root shell with no will-run line and no PROD confirmation — the most dangerous action in the app had the least friction — and a node-only second key contradicts `x` being the one shell key. **The key goes; its command becomes this screen's default.** Nothing else about it was ever specified, so there is no other behavior to preserve.
- Rows: `image busybox:1.37` (`i` edit), `profile sysadmin` in `Warn` (`p` cycle · host pid + privileged), **`shell chroot /host · bash, else sh`** — "you land on the node's filesystem, not the container's", `lands in kube-system` — "a real pod on this node · deleted when you exit".
- **The entrypoint is the default, not homework.** `chroot /host` + bash-preferred/sh-fallback is what `s` already did; the panel ships that shell rather than instructing the user to chroot after landing. The `shell` row is descriptive — the entrypoint is fixed, not an editable field.
- **The node's own pod count is the warning** — `⚑ root on worker-01 — 62 pods are running here` — a number from the data, not a scare string.
- `will run`: `kubectl debug node/<name> -it --image=busybox:1.37 --profile=sysadmin -- chroot /host sh -c 'command -v bash >/dev/null && exec bash || exec sh'` (panel is ~940px-equivalent so this does not clip). PROD adds the inline `y/N`; the red modal still belongs only to delete and drain.
- Prefilled to exactly the legacy defaults, so **`x ↵` is the old `s`** — one extra keystroke buys the visible command and the PROD confirmation. Keys: `↵ root shell · i image · p profile · esc cancel`.
- Suspend/restore and the keybar failure line `node shell exited: …` carry over from `s` verbatim — same handoff as exec (10a).
- Sits in the nodes verb set next to `C` cordon and `ctrl+d` drain, so the escalation ladder reads on one keybar.

### 41e — Ephemeral containers in pod detail (after the fact)
- An ephemeral container is **permanent state on someone's pod**, so pod detail (5a) grows an `EPHEMERAL` group under CONTAINERS: heading in `AccentHi` + `attached by debug · not part of the spec` + right-aligned count.
- Row: `⚑` glyph (`Accent`) · name `debugger-7xk2` · `<image> → <target>` dim · state · age; under it, one `TextGhost` line: `cannot be removed — it leaves when the pod does`.
- **Zero chrome until earned** (13d): no ephemeral containers → no group, and no `⚑` tag on the pods-table row. One exists → both appear.
- `↵ re-attach` (a dropped connection costs one key, not a second injected container) · `l logs` · `↹ cycle container`. Ephemeral containers participate in the container cycle and the log view's container list like any other container.

## Interactions & Behavior (system-wide)
- **One palette shell, three scopes:** `g` (anything) · `n` (namespaces) · `c` (contexts). Opening any of them pre-selects the most recently visited *other* entry of that scope (alt-tab semantics, like editor Ctrl-Tab), so `↵` with no typing toggles straight back to it — same two keystrokes the old double-tap used, now visible through the palette. All share the same fuzzy input, selection treatment, and keybar footer.
- `g` opens the jump palette anywhere. Empty query = alias letters + ranked daily kinds (12a); typing = fuzzy results across kinds/resources/namespaces/contexts (2b/12b). `esc` closes; `↵` jumps.
- `/` opens filter on the current view (table rows or log stream). Show `matched/total` and a "N hidden by filter — esc to clear" notice so items never silently disappear. Highlight matched characters in results.
- `↵` opens the selected resource's full view; `esc` walks back one level (detail → table; palette/filter → close). While a filter is being typed, `↵` never opens a destination (even for a kind that has one) — it commits the filter instead, keeping the query/rows/chrome as-is but releasing keys back to normal list navigation and verbs; a second `↵` then opens the selected row's destination same as unfiltered. `/` on a committed filter resumes editing the same query.
- **Generic navigation stays out of task keybars:** plain `↵ open` is taught once in the help overlay's LIST column and `esc back` once in its MISC footer row, both omitted from every screen's bottom band. Screen-specific Enter/Escape actions (`↵ pods`, `↵ edit`, `↵ open object`, `esc clear`, `esc cancel`, …) still render where they add information; per-screen key lists elsewhere in this document describe behavior subject to this keybar rule.
- `j/k` and `↑↓` are synonyms for movement everywhere; in pod detail (5a) `[/]` moves to the next/prev sibling pod, and in generic custom resource detail (14d) `j/k` still means next/prev sibling resource.
- Connection loss: switch to 4a automatically; keep the last snapshot; retry with exponential backoff and a visible countdown; disable mutating verbs. On reconnect, silently return to live and drop the stale strip.
- RELATED/CONTROLLER links, and every detail screen's own pre-filled "jump to related object" action (9b/16a-b/23a-b/19a's `↵`), reuse the goto navigation `g` itself uses: a fresh browse view opens on the target kind with the row selected, pushed on top of the screen the jump was fired from — one `esc` back returns to it, the same contract every other pushed screen gives.
- **Destructive-action policy:** reversible-and-immediate verbs (cordon) execute right away; delete and rollout restart are both tiered — inline `y/N` in non-prod, type-the-name modal in PROD contexts; drain and force-delete get the modal always, and so does deleting a Namespace, CRD or Node (type-the-count for a marked set). The PROD flag comes from `config.yaml`'s `prodContexts` (toggled with `ctrl+p` in the context palette), never a name heuristic; a `prodContexts` that can't be read treats every context as PROD.
- `x` execs: single container → straight to shell; multiple → picker (10a). App suspends, shell takes the tty, exit restores the exact prior state.
- `e` opens events (namespace-scoped from a list view; object-scoped from a detail view). `↵` on an event navigates to its object.
- `y` opens the YAML view on any selected object, any kind.
- `g <alias> ↵` is the canonical kind jump: alias letters re-rank (pin to rank 1), never fire instantly. Aliases: p pods · d deployments · s services · i ingresses · n nodes · c configmaps · e events. First-letter highlights render only on these.
- `f` starts a port-forward from any pod/service/deployment row (13a). Sessions live in the Forwards registry kind (13c); the header chip (13d) appears only while sessions exist. Forwards die with the app, survive context switches, and never interrupt other screens on failure.
- CRD kinds are discovered per context at connect and cached; they get list (14a), detail (14d), goto (14c), and all generic verbs with zero configuration — this is the payoff of the kind registry + command table architecture.
- `t` opens the incident timeline (namespace-scoped from lists, object-scoped from detail); `↵` on a line goes to the object.
- `e` inside the YAML view enters edit mode (17a): dry-run before apply, watch paused, conflicts surfaced — never silent overwrite.
- `+`/`−` on scalable workloads opens the inline scale prompt (17b); `0` scales to zero. Reversible tier — no modal.
- `space` marks / `*` marks all filter matches / `esc` clears (20a). Set-capable verbs act on the marked set; PROD bulk delete = type-the-count modal.
- `x`/`X` reveal secret values in the YAML view (21a); re-masked on exit; `y` copies decoded.
- `w` on a 403 card opens who-can pre-filled (22a); also reachable as a registry kind via `g`.
- Helm releases browse without the helm binary; rollback shells out with a `will run` line (18a).
- Ingress/HTTPRoute `↵` opens a live routing table (23a/23b) — backends resolved from the watch, never a describe page; `p` on an HTTPRoute opens its parent Gateway.
- `i` opens the set-image/tag editor on a Deployment, StatefulSet, DaemonSet, or CronJob row (24a); CronJob changes affect future Jobs only. History comes from the watch cache, never a registry call.
- `r` on a workload row opens the resources editor (25a); uppercase `R` remains rollout-restart on Deployments (inline `y/N` confirm).
- `m` opens the labels/annotations editor (26a) on any object, CRDs included; selector-linked labels carry an inline join warning before you can edit them.
- ConfigMap/Secret `Data` views: `↵` edits a value in place (27a), `a` inserts a new key as a line-insert (27b); `ctrl+r` on a ConfigMap value chains the apply with a rollout-restart of every consumer.
- `U` opens the what's-new/update panel from anywhere (28a/28b), also reachable as `:update`; kute checks once per 24h and never self-updates — it only prints the detected package manager's upgrade command.

## State Management (suggested Bubble Tea model shape)
- `mode`: `browse | filter | goto | detail | logs | offline | error | noCluster` — drives keybar contents + mode pill.
- `location`: context / namespace / kind / (resource) — rendered as the breadcrumb.
- `snapshot`: last successful resource list + `fetchedAt` (for the 4a stale stamp).
- `connState`: `connected(latency) | reconnecting(attempt, nextRetryAt) | failed(error)`.
- `palette`: query, results, selection, recents (persist recents across sessions).
- `filter`: query per view; saved-view slots optional (was explored in 1b; not part of the decided scope).
- `perContext`: map of context → last namespace/kind/filter (restored on context switch), plus that context's own namespace-recents list — a namespace only exists inside its own cluster, so unlike kinds/contexts its recents aren't a single global list. `recentKinds`/`recentContexts` stay global (kinds/contexts exist across every cluster) and back their palettes' alt-tab pre-selection filtered to what the current context actually has.
- `probes`: async reachability results for contexts (latency or error), refreshed on palette open.
- `forwards`: list of {localPort, target(kind/name/port), resolvedPod, namespace, context, state(active|reconnecting(attempt,nextRetryAt)|stopped), startedAt, lastTrafficAt, bytesPerSec} — global, session-scoped, drives 13c rows + 13d chip.
- `discovery`: per-context cache of API resources (group, version, kind, scope, printer columns, established) with fetchedAt — feeds the kind registry, goto corpus (14c), and CRDs list (14b).
- `marks`: per-view set of marked object keys (cleared on kind/namespace switch); keybar + strip + confirm policy read its size.
- `reveal`: per-secret set of revealed data keys — in-memory only, cleared on view exit; never serialized.
- `whoCan`: current query {verb, resource, namespace} + resolved subject rows (from cached bindings/roles).
- `editBuffer`: YAML edit state {baseResourceVersion, text, dirty, dryRunResult|conflict} — exists only in edit mode.
- `timeline`: merged feed window (events + restarts + rollout revisions) per scope.
- `imageHistory`: per-workload tag history derived from the watch (controller revisions where available + cross-namespace image sightings) — feeds 24a, no network calls of its own.
- `updateCheck`: {lastChecked, lastAttempt, latestVersion, seenVersions} — cached in the state dir, drives the 28a chip and 28b's per-version dismissal; `lastAttempt` holds a failed check's retry back to once an hour; absent/inert when `update.check: false`.
- Watch streams update the table in place; metrics poll on the `sync` interval shown in the header.

## Design Tokens — semantic, two themes

The app supports **dark and light themes**. Implement colors as a single semantic `Theme` struct — every view renders through it; **no hex literal ever appears in view code**. The mockup HTML shows the dark theme; light values below are the decided equivalents (not naive inversions — status colors darken/saturate to hold contrast on light backgrounds).

The per-screen sections above cite dark hexes (they describe the mockup); resolve each to its semantic token via this table when implementing.

Theme selection: default = terminal background detection (`lipgloss.HasDarkBackground()` at startup), overridable by `--theme dark|light|auto` and a config-file key. Don't use `lipgloss.AdaptiveColor` per-color — the struct swap is the mechanism, so an explicit override is trivial.

Rules that hold in both themes:
- Text hierarchy is a 6-step ramp `Text → TextGhost` (contrast descends; on light the ramp runs dark→pale, never re-order roles).
- Bar track `BarTrack`; bar fill `Accent`, `Warn` ≥70%, `Bad` at limit. Warn numbers in YAML use `Warn`.
- Red borders (`ConfirmBorder`) remain reserved exclusively for destructive confirms.
- Mode pills by hue: purple = normal modes · blue = ALL NS · red = OFFLINE/CONFIRM · gray = SETUP. Pill bg = the theme's tinted surface, pill text = the hue's text token.
- Selection cue = 1-cell accent bar + `SelBg` row background — verify it in both themes; the bar is the primary cue.
- Text fields horizontally scroll to keep the caret visible. `shift+←/→`, `ctrl/alt+shift+←/→`, and `shift+home/end` select text; typing or paste replaces it, backspace/delete removes it, and `ctrl+shift+c` copies it when the terminal forwards that chord. In-field selection uses `Accent` behind `Bg` text so it stays distinct even inside a `SelBg` row. A masked Secret field never reveals the selected span's length.
- Contrast floor (pinned by `internal/tui/theme_contrast_test.go`): status, error, body-text and `TextDim` hint tokens reach WCAG 4.5:1 on every background they're drawn on, `SelBg`/`MarkBg` included (and `ErrBannerBg` for `TextDim`); the deliberately muted 4a ramp and `AccentMuted` reach 3:1. The decorative tokens (`TextFaint`, `TextGhost`, `YamlPunct`, `YamlFold`) are exempt.
- 4a desaturation: each theme defines its own muted ramp (dark: dim the colors; light: wash toward gray) — don't compute it, declare it in the struct.
- Test on a real light terminal and on 256-color fallback; hex values degrade via termenv.

Status glyphs: `●` running · `▲` pending · `✕` failed/crashloop · `○` completed · `◌` disconnected/probing · `↺` restarts · `⧗` stale · `▶` following · `▲` warning/version-skew · `◈` cordoned · `∗` all namespaces · `⇄` port-forward.

Loading spinner: `⣾⣽⣻⢿⡿⣟⣯⣷` at 10fps — the one animated mark in the app, shared by every loading header, strip, and body (15a) so they all move identically. Not in the status vocabulary above: it says *in flight*, never a resource's state.

Typography: single monospace face (mock uses JetBrains Mono; the terminal's font applies). Weight via bold only. Uppercase + letterspacing for section labels/column headers.

## Architecture notes
The enforceable rules distilled from this design (kind registry not hardcoded views, actions as a command table, cluster access behind an interface, versioned persisted state, pure rendering, terminal capability degradation) live in `CLAUDE.md`'s Invariants and Conventions sections — that file is the one to keep in sync, not this list.

## Mapping HTML → terminal
- 1 row of table/list = 1 terminal line. Strips, keybar, header = 1 line each.
- 2px left selection border = a 1-cell colored bar (`▎` or bg on first cell) + row bg `#1d1633` via Lip Gloss background.
- Progress bars = block glyphs (`█▓░` or `▰▱`) ~6–8 cells wide, colored per token rules.
- Rounded corners/shadows on the palette = Lip Gloss rounded border; "dim the backdrop" = re-render the table through a faint style.
- Desaturation in 4a = swap the color ramp for muted variants (no filter support in terminals).
