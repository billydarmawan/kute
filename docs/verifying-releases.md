# Verifying a release

Every kute release archive is signed, and the release carries a build provenance
attestation. This page is how you check both by hand.

`checksums.txt` — which both installers verify — proves the archive you got matches the
manifest that came down the same wire. It does not prove the release is ours: anyone who
could tamper with the archive could tamper with the manifest beside it. The signature is
what makes the download *attributable*, which matters for a tool that reads your kubeconfig
and can delete production workloads.

## What a release contains

For each of the six platform archives (`kute_<version>_<os>_<arch>.tar.gz`, `.zip` on
Windows — linux, darwin and windows, each on amd64 and arm64):

| File | What it is |
| --- | --- |
| `<archive>.sigstore.json` | A [Sigstore bundle](https://docs.sigstore.dev/about/bundle/): the signature over the archive, the short-lived Fulcio certificate it was made with (whose identity names the workflow and tag that produced the release), and the transparency-log proof, in one file. |
| `<archive>.sbom.json` | An SPDX SBOM of the archive, generated by [syft](https://github.com/anchore/syft). |

Plus `checksums.txt` for the release as a whole, with its own `.sigstore.json`.

Signing is **keyless**: there is no kute public key to distribute or rotate. The signature
is bound to an ephemeral certificate issued to the release workflow's OIDC identity, and
recorded in the public [Rekor](https://docs.sigstore.dev/logs/overview/) transparency log.
What you verify is *who signed it*, not *which key signed it* — so the check below names an
identity, and that is the part that must match.

## Verify the signature

Needs [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) — v3 or newer
for the command exactly as written; see the note below if yours is older. Set `VERSION` to
the release you downloaded, without the leading `v`:

```sh
VERSION=0.4.0
FILE=kute_${VERSION}_linux_amd64.tar.gz
BASE=https://github.com/kute-dev/kute/releases/download/v${VERSION}

curl -fsSLO "${BASE}/${FILE}"
curl -fsSLO "${BASE}/${FILE}.sigstore.json"

cosign verify-blob \
  --certificate-identity-regexp '^https://github\.com/kute-dev/kute/\.github/workflows/release\.yml@refs/tags/' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  --bundle "${FILE}.sigstore.json" \
  "${FILE}"
```

Success is one line:

```
Verified OK
```

Anything else — including a certificate whose identity doesn't match — exits non-zero. Treat
that as a failed download, not a warning.

On cosign 2.x, add `--new-bundle-format` — that release reads the bundle only when asked.
cosign 3 made it the default and dropped the flag, along with the `--signature`/`--certificate`
pair the older split `.sig`/`.pem` layout needed.

To pin the check to one exact tag rather than any kute release, swap the regexp for the
literal identity:

```sh
  --certificate-identity 'https://github.com/kute-dev/kute/.github/workflows/release.yml@refs/tags/v0.4.0'
```

To verify the manifest instead of an individual archive, run the same command against
`checksums.txt` and `checksums.txt.sigstore.json`, then `sha256sum -c checksums.txt
--ignore-missing`.

## Verify build provenance

The signature says who signed the archive. Provenance says *what built it* — which
repository, workflow, commit and runner — attested by GitHub rather than by us. Needs the
[`gh` CLI](https://cli.github.com):

```sh
gh attestation verify --repo kute-dev/kute "${FILE}"
```

The two checks are independent and worth running together: a signature with the right
identity and provenance naming an unexpected source commit is a different kind of problem
from either check failing on its own.

## The SBOM

Each archive ships an SPDX SBOM listing the Go modules compiled into that binary — the input
to a "does this ship the vulnerable version of X" question that doesn't require trusting our
answer:

```sh
curl -fsSLO "${BASE}/${FILE}.sbom.json"
grype "sbom:${FILE}.sbom.json"     # or: syft convert, or read it directly
```

kute's own dependency scanning runs
[`govulncheck`](../.github/workflows/govulncheck.yml) weekly, which reports *reachable*
vulnerabilities rather than merely present ones. The SBOM is for scanners that want the
inventory.

## What the installers do for you

[`install.sh`](../website/install.sh) and [`install.ps1`](../website/install.ps1) verify the
signature automatically **when `cosign` is on your `PATH`**, using the same identity as
above, and always verify the checksum. Without cosign they print a note and fall back to the
checksum alone — a check nobody can run is not a stronger check, but it does mean the
default `curl | sh` path on a machine without cosign is checksum-only.

If you want the strong check on a machine that doesn't have cosign, install cosign first, or
follow this page by hand.

Releases published before signing landed (`v0.1.*`–`v0.3.*`) have no `.sigstore.json`; the
installers say so and continue. Anything from `v0.4.0-beta.1` onward is signed, and the
installers enforce that: with cosign present, a bundle that can't be downloaded for one of those
releases (deleted, 404, network) stops the install rather than falling back to the checksum —
removing the bundle is exactly what someone who replaced the archive and `checksums.txt` would do.

## Reporting a problem

A verification failure you can't explain is a security report, not a bug report — see
[SECURITY.md](../SECURITY.md), which asks you to use GitHub's private advisory form rather
than a public issue.
