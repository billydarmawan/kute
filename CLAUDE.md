# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TUI Kubernetes console (Bubble Tea + Lip Gloss). 

Design spec: `docs/design/README.md` (source of truth for screens, layout, tokens, keys, glyphs).

`docs/lazy-informers.md` explains how the data layer decides what to fetch and when — read it before changing anything about informer startup, cache reads, or discovery.


## Invariants — never violate

- **No hex color literals in view code.** All colors come from the semantic `Theme` struct (dark + light variants live in one file). New UI = new token if needed, never an inline color.
- **Both themes always.** Any new surface must define/reuse tokens that work in dark and light; test both.
- **Every verb goes through the command registry.** Key, label, destructiveness tier, applicable kinds — keybar, help overlay, and confirm flow render from it. Never hand-wire a keybinding in a view.
- **Destructive-action policy:** reversible-and-immediate verbs (e.g. cordon) execute right away; delete and rollout restart are both tiered — inline y/N in non-prod, type-the-name modal in PROD contexts (`config.yaml`'s `prodContexts`, never a name heuristic — and a config that fails to parse fails *closed*: `config.Load` salvages what decodes, an unreadable `prodContexts` makes `IsProd` true for every context, `tui.BuildConfigChip` shows it on every screen's header, and `SetProd` refuses to overwrite the file; it is also the file's only writer, and a surgical one: it re-reads the file at write time and edits only `prodContexts` on a `yaml.Node`, written temp+fsync+rename, so per-invocation overrides like `--no-update-check` live in unexported `Config` fields and can never be persisted); drain/force-delete always modal, and so is deleting a Namespace, CRD or Node (type-the-count for a marked set). The whole policy — tier *and* whether a modal types the name or is a y/N card — is one table, `verbs.Resolve(verb, target, isProd)` (`internal/tui/verbs/policy.go`, pinned verb-by-verb by `TestResolvePolicyTable`). `actions.Controller.Begin(actions.Request{Verb: …, Prod: …}, action)` resolves it itself and takes no tier, so a call site can't pick one; the only screens that call `verbs.Resolve` directly are the bespoke gates `actions/guard_test.go` allow-lists (kubectl edit/debug handoffs); 20a's marked-set delete goes through `Begin` with `Scope.BulkTargets` like §36c's marked-set suspend. Force-delete escalates through `Controller.EscalateForceDelete` on `verbs.ForceDelete.Key` (`ctrl+k`) — never a local `kind ==` check, a hard-coded key, a verb-name list, or a staged inline "force" sub-state. Red borders are reserved exclusively for destructive confirms.
- **Resource kinds are registry entries**, not bespoke screens. New kind = columns + status derivation + verbs registered on the shared list/detail skeleton.
- **Render functions are pure**: f(model, theme, size). No I/O, no clock reads, no globals in render paths.
- **All cluster access goes through the `ClusterProvider` interface.** UI code never imports client-go directly. The fake provider must stay feature-complete for tests/demo mode. The two lister decorators in `internal/app` embed `resources.RawLister`, which promotes only `ListRaw` — every optional seam (`Synced`, `KindSynced`, `CountLive`, …) needs an explicit forward, and a missing one is *silent*: the consumer type-asserts, misses, and takes its fallback path. Add the compile-time assertion in the same commit as the seam. One unforwarded `CountLive` made the jump palette count informer caches instead, starting an informer per kind on the update loop and hanging the app for a minute.
- **The app pays for the screen you're on.** Connect starts three informers (Namespace, Pod, Node); every other kind's informer starts when something first reads it, from inside `ListRaw`. Two rules follow and are easy to break by accident: **never read a cache breadth-first** (a loop over every registered kind starts every informer — that's what `Cluster.CountLive`'s one-object metadata list exists for, and why the goto palette and empty-state hints skip un-started kinds), and **never gate a loading state on `Synced()`** — it's a connect latch, not cache state; `KindSynced(kind, namespace)` is the per-kind, per-namespace answer, and it deliberately reports settled for anything that will never arrive (stopped cluster, no informer, Forbidden, or an initial LIST that keeps failing) so a spinner can't hang. Settled is not the same as empty: `KindError(kind, namespace)` carries the reason a cache stopped filling and **must** be shown when it's non-nil (`tui.KindsError`, right after the `KindsSynced` gate) — without it the anti-hang rule just trades a spinner for the false claim that the cluster has none of that kind. A screen reading a kind it doesn't display must also reload on it (`browse`'s `auxKinds`), or its cells go stale. **An empty state is a claim about the cluster** — never enter one without checking the backing caches have filled (`tui.KindsSynced` + `ScheduleCacheSyncRetry`); the retry matters because a kind with genuinely zero objects syncs without emitting a change event, which is exactly the case where "empty" is correct. The `namespace` argument to all three matters: by default every cache is cluster-wide and normalizes to `""` regardless of what's passed, so this is a no-op invariant for a plain `kute`. Under **`--namespace-scoped=<ns>`** (`docs/lazy-informers.md` §5.6) a namespaced kind gets one cache *per namespace actually read* — `Cluster.cacheScope` is the single place that mode is consulted — so a caller **must ask about the same namespace its own read used**; asking about the wrong one (or a bare `""` when the read was scoped) answers for a cache that was never started. `""` always means the explicit cluster-wide/all-namespaces cache, started on demand even in scoped mode — it is never silently downgraded to the active namespace.
- **Persisted state is versioned.** Any change to the recents/perContext schema bumps the version and adds a migration.
- **One palette shell** parameterized by scope (goto/namespace/context) — never fork it.
- **Aliases are reserved for the ~8 built-in daily kinds** (p d s i n c e) and are always the kind's first letter, rendered as a highlighted first letter — never a chip. Aliases re-rank to rank 1, never fire instantly. CRDs and the long tail never get them.
- **CRD support is data, not code.** Discovered kinds become kind-registry entries from API discovery (printer columns → columns, Ready-style condition → status, else neutral). No per-CRD layout code, ever. **Flux (§30a) is the one curated exception**, on the ground that its five API groups are a fixed, versioned, documented status vocabulary rather than the unknown long tail — a generic Ready read renders a healthy GitOps cluster as a column of red, since `Ready=False, reason=Progressing` is normal and a suspended object's conditions are frozen. It is recognised **by API group, never by bare kind name**: Flux's `HelmRelease` collides with §18a's synthetic Helm-3 kind, and because `resources.Registry` is keyed on the Kind string alone with last-write-wins `Register`, a name match silently replaced the Helm list *and* hid every Flux HelmRelease. Kinds whose registry key is not their API Kind live in `kube.substitutedKinds` (curated) or get a `kube.QualifiedKind` key `<Kind>.<group>` at discovery (any CRD whose Kind is a built-in key, is owned by another group in `kube.ownedKinds`, or collides with another discovered group) — a discovered kind never takes a key something else holds; anything sending a kind back to the API server or to kubectl must go through `ResourceKind.APIKind()`/`.ResourceArg()`, never `string(kind)`. Deleting a CRD always gets the type-the-name modal (`verbs.Resolve`'s cascade-kind rule). Discovery must never list CRD *objects* — they carry the full OpenAPI schema for every served version (2.76 MB across 48 CRDs on a real cluster, 98% of it unread). It reads CRD *names* via the metadata client plus the discovery API; printer columns arrive per-kind on first read, so "else neutral" is the interim state of a real kind, not only a fallback for CRDs that declare none.
- **Forwards are a registry kind** on the shared list skeleton, global and session-scoped; a failing forward may only change the header chip color — never a modal or banner over unrelated screens.

## Conventions
- Status glyphs, key vocabulary, and mode-pill hues per the design README — don't invent alternatives.
- `j/k` ≡ `↑↓` everywhere; `esc` always walks back exactly one level.
- **A node bar's denominator follows its numerator.** metrics-server usage is measured across the whole machine (kubelet, runtime, everything), so a usage bar divides by `Status.Capacity` — that's what `kubectl top node` does, and on a managed node with ~3Gi reserved, dividing by Allocatable instead overstates every bar by ten points. A bar whose numerator is a *request* sum divides by `Status.Allocatable`, and so does PODS. Both come from `kube.NodeAllocatable`/`kube.NodeCapacity`, the one place either is derived — browse, nodedetail and overview each used to re-read `Status.Allocatable` inline, which is exactly how 11a and 11b came to report different memory for the same node. Request sums go through `kube.PodEffectiveRequests` (native sidecars + init-phase peak + `spec.overhead`; pod-level `spec.resources` replaces the container sum for each resource it sets; an in-place resize counts the largest of spec, allocated and actual — status alone when the resize is Infeasible), never a bare loop over `spec.containers`, which understates every mesh-injected pod; `kube.Pod.CPURequestMilli`/`MEMRequestBytes` stay the literal container sum and describe the pod, not its footprint on a node.
- **Pod-metrics maps are keyed by `kube.PodKey(namespace, name)`, never bare name.** Callers pass `""` for cluster-wide reads, where same-named pods in different namespaces (a DaemonSet, one chart installed twice) silently overwrite each other and a row shows another pod's usage.
- Watch-based updates, not polling (metrics poll on the sync interval only; 11b's disk row reads the kubelet summary API for the one node on screen at 1/15th of that rate, and stops on Forbidden — never widen it to a per-node sweep, since each summary carries every pod's stats). The six deliberate one-shot reads are `CountLive` (palette counts, which must not start informers), 8a's live `managedFields` fetch, 13a's `Pods.Get` of each forward's resolved pod (`ForwardManager.ReconcilePodTargets`, issued per debounced Pod-event flush, at most one in flight per forward, so a deleted pod drops its tunnel into reconnect — the events come from the *current* context's Pod informer only, so a forward started under another context is checked only when this one's pods change and otherwise learns its pod is gone when its tunnel's `Run` fails), a cached `Discovery().ServerVersion()` read taken once at connect/context-switch, a cached `SelfSubjectReview` (`authentication.k8s.io/v1`, `v1beta1` only when v1 isn't served) taken once at connect/context-switch right after it, and the live `SelfSubjectAccessReview` issued when a Pod DEBUG panel opens or changes mode — none is a poll. The self-subject review is the server's own answer to "who am I" (`Cluster.ReviewedIdentity`, `kube/identity.go`; `fake.Cluster.SetReviewedIdentity` in tests/demo): its username and groups are who-can's (22a) pinned "(you)" identity and its username is §33a's Argo sync `operation.initiatedBy.username` (else `kute`), because for token/OIDC/exec-plugin auth the kubeconfig only knows its AuthInfo entry name. Cleared on context switch; any failure (Forbidden, pre-1.27 server, transport) leaves it unset and consumers fall back to the kubeconfig identity — never retried, never re-issued per screen open. The version read backs a tri-state `supported`/`unsupported`/`unknown` capability stored on the stable cluster/fake context (Kubernetes 1.27+ supported, below 1.25 unsupported, 1.25–1.26 unknown unless an already-populated `spec.timeZone` on the object itself is direct evidence of support) and is injected as a package-local capability interface into `tasks/cronjobschedule` (36d) to gate timezone editing — never inferred from Node kubelet versions, and never risked as a write that an older API server could silently prune. The access review is the authoritative launch gate (`create pods/ephemeralcontainers` for attach, `create pods` for copy); the cache-local who-can resolver may explain an explicit denial but must never gate `x`, since its RBAC-only view cannot represent every authorizer or authenticated group.
- Terminal capability degradation: 256-color palette mapping (via termenv) and ASCII substitutes for exotic glyphs (`◈ ⧗ ▐ ◌`) are the decided fallback path; a minimum-terminal-size guard screen is decided but not yet built.
- **Every cluster read parents on the session's context** (`internal/tui/sessionctx.go`). `Session.ClusterContext()` is the parent for anything read *through* the active cluster — captured in a `tea.Cmd`'s prologue alongside every other Session read, then given the screen's own `context.WithTimeout`; it is cancelled on quit *and* on a context switch, so a slow list against the cluster you just left can't land in a screen now showing a different one. `Session.Context()` is the process context (quit only) and is for work that isn't cluster-bound: probing every kubeconfig context (7a/4c), the update check, and the context switch itself — which must survive the very reset it performs. `context.Background()` in a read path is a bug; the deliberate exception is every write in `actions.Controller`, since cancelling a mutation mid-flight doesn't un-apply it and would report a committed change as a failure. The cancel-before-you-swap ordering is load-bearing: `ResetClusterContext` runs *before* the rebuild starts (`switchContextCmd`, `app.attemptReconnect`/`attemptSwitchContext`), because the blocking cache re-sync is exactly the window in which stale reads would otherwise complete.
- **Every text buffer routes paste through `tui.RoutePaste`** (`internal/tui/paste.go`), called at the top of the screen's `Update` with a `pasteTarget()` resolver that mirrors that screen's own key-routing precedence and returns nil when no buffer is open. A screen that only handles `tea.KeyPressMsg` silently drops every paste: a terminal's bracketed paste arrives as one `tea.PasteMsg` that never passes through a key handler, and bubbles' own `ctrl+v` binding answers with an unexported message no screen can route (which is why `RoutePaste` claims the chord first and replies with `tui.PasteCmd`). Two silent-failure traps in a resolver: build it on a **pointer** receiver, and point it at the **focused** buffer — `textinput.Update` no-ops when blurred. If the edit has a side effect (re-filter, re-match, clamp), do it inside the returned closure, or a pasted query will sit in the box without narrowing anything.

## Workflow
- Before committing/pushing, run `go vet ./...` and `golangci-lint run` — the same two checks CI's `quality` job runs. Catches things like an ineffectual assignment in a test locally instead of in CI.
- After UI changes, run the golden-file snapshot tests (both themes) and update intentionally-changed snapshots only.
- New screens/verbs: update the command registry and kind registry first; views follow.
- Commit messages: `type(scope): short imperative description`, lowercase, one focused line, no trailing period, no Co-Authored-By. Match the granularity of the change — e.g. `build(deps): bump go module dependencies, k8s.io to v0.36.2`, `ci(pages): pin workflow actions to commit SHA`. Avoid vague messages like "update deps" or "fix stuff"; name what actually changed. `feat`/`fix`/`perf` subjects flow verbatim into the release changelog and 28b's what's-new panel (git-cliff, see `cliff.toml`), so write the description as the user-visible *effect*, not the implementation: `fix(tui): stop the 7b help overlay truncating every key-hint row` is a good subject; `fix(verbs): give the dead Mutating field a real reader` means nothing to a user and git-cliff can't fix prose, only filter it.

Tooling is pinned via **mise** — `mise.toml` is the authoritative list of versions (go, kubectl, golangci-lint, git-cliff, govulncheck, kind, betamax, and `gopls`, which backs Go code intelligence via the LSP tool; prefer `findReferences`/`goToImplementation` over grep when changing an interface seam like `ClusterProvider`/`RawLister`/`Mutator`, where a missing forward behind an embedded type is silent). `KUBECONFIG` is set in `mise.toml` to `{{config_root}}/.kube/config` (repo-relative, gitignored — every checkout gets its own, no machine-specific setup needed); the app also falls back to `~/.kube/config` and then in-cluster config. Run `mise install` to get the pinned toolchain.

## Architecture

Layered, with the TUI depending on `kube` only through interfaces so screens can be tested without a live cluster.

- **`cmd/kute/main.go`** — thin entry point; calls `app.Run()`.
- **`internal/app`** — composition root. `NewModel` builds a `kube.Cluster` (real cluster, informer-backed) or a `kube/fake.Cluster` (`--demo`) and roots the model at `tasks/browse`, injecting it as the `resources.RawLister` and `browse.MetricsReader` seams and wiring an `OpenLogsFunc` that pushes `tasks/podlogs` for the selected pod. `RunWithConfig` starts the eager informers (or the demo fake's event loop) and pipes both resource-change and connection-state events into the program. If no cluster is reachable and `--demo` isn't set, `browse` still renders, in an error state carrying the real connection error (`browse.Config.InitErr`). This is the only place real Kubernetes wiring happens.
- **`internal/diag`** — the diagnostics sink (`docs/diagnostics.md`): `--log-file`'s destination for the error/klog stream, and the writer of crash reports. klog points at it instead of `io.Discard`, so **without `--log-file` the stream still fills a bounded in-memory ring** — that ring is what puts the cluster's last 300 log lines in a crash report from a run nobody thought to instrument. `app.crashCatcher` wraps the root model and **records then re-panics**: Bubble Tea's own recover is what restores the terminal, and it can only do that if the panic keeps travelling. Everything a report says about *where the user was* is cached on the update loop (`liveState.sync`) precisely so a dying informer goroutine reads a copy instead of racing `Session.Location`. One panic site stays out of reach by construction — Bubble Tea recovers `tea.Cmd` goroutines internally and surfaces only `ErrProgramPanic` — so `reportProgramCrash` writes a report saying the value is unavailable rather than letting the run look clean. The crash footer and `.github/ISSUE_TEMPLATE/bug_report.yml` ask for the same fields in the same order; keep them in step.
- **`internal/kube`** — Kubernetes access. Defines domain structs (`Pod`, `PodMetrics`, `Context`, `ResourceKind`, `ConnState`, `Event`), one-shot/`Client*` readers, and `Cluster` (shared informer factory + `PodMetricsByNamespace` + watch/conn-state events). Every typed kind's informer, cache reader, GVR and scope lives in **one `typedKinds` table** (`watch.go`) — the single registration path, because reaching for a factory's `Lister()` registers that informer as a side effect, and a registration that skips the table gets started later with no watch-error handler attached. `ListRaw` dispatches through it and calls `ensureKind` first, which is where laziness lives; `KindSynced(kind, namespace)` is the per-kind cache-fill signal the UI's loading states gate on, and `CountLive` counts a kind server-side (`limit=1`, `remainingItemCount`) without touching an informer. Caches strip `managedFields` on the way in (`transform.go`), so the one screen that shows them (8a) fetches them live. Helm releases get their own Secret informer, filtered server-side to `type=helm.sh/release.v1`, rather than reading the shared Secret cache — and one such informer *per namespace read* rather than a single cluster-wide one — a namespaced read is served from the all-namespaces cache only once that has already synced (release Secrets are individually large: 8.19 MB cluster-wide against 4 MB for one namespace on a real cluster, which over a VPN is the difference between a screen that loads and one that never does — see `docs/lazy-informers.md` §5.5 before generalising it to another kind). TLS cert reads (routetable's expiry cell, certchain's Secret ref) are the one other user of that shape: `ListTLSSecrets`, filtered to `type=kubernetes.io/tls`, one informer per namespace read, gated on the synthetic `KindTLSSecret` key — never `ListRaw(KindSecret)`, which starts the cluster-wide full-payload Secret cache (§5.7). Write access is the narrow `Mutator` interface (`DeleteResource`, `DeleteResourceForced`, `Cordon`, `Drain`, `RolloutRestart`), implemented on `Cluster` and called from `browse`/`poddetail` (delete), `browse`/`nodedetail` (cordon/drain), and `browse` (Deployments' `R` rollout-restart, inline `y/N` confirm) via `actions.Controller`. Event reads (`ObjectEvents`, `NamespaceEvents`) back `poddetail`'s EVENTS grid and the `events` (9b) screen. **Exec credential plugins (GKE/EKS/kubelogin) never touch the terminal** (`execauth.go`; the user-facing account is README.md's Authentication section): every REST config gets `ExecProvider.StdinUnavailable`, and client-go's Authenticator is constructed with `os.Stderr` swapped for a pipe kute drains — both decisions are frozen at *first client construction* for a given exec config, so they belong in `newClientForContext` and nowhere else. A credential failure is its own `ConnPhase` (`ConnUnauthenticated`), counts as `Offline()`, carries the plugin's own stderr in `ConnState.Err`, and **stops the /livez ping loop** — re-running a plugin that just failed is not a retry strategy, so recovery is 4a/4c's explicit `r`. Consuming *read* interfaces (`resources.RawLister`, `browse.MetricsReader`, …) are declared **in the packages that use them**, not here — so `kube` has no dependency on `tui`.
- **`internal/resources`** — the resource catalog: `Descriptor`/`Registry` (per-kind columns, projection, health tallying/labeling), `Group`s, `columns.go` (`components.Column`/`Cell` specs per kind), and `List`/`Count` over a `RawLister`. Kind-agnostic; drives `browse`.
- **`internal/tui`** — root model (`Model`, task stack, palette/help overlay routing), Chrome v2 (`Screen`/`Frame`), the semantic `Theme`/`Styles`, `glyphs.go`, `verbs` (the keybar/help/confirm verb registry), and `actions` (the shared confirm→execute controller). No pre-redesign chrome remains as of Phase 6.
- **`internal/tui/components`** — reusable stateless renderers: `table` (the inverted-layout table), `bar` (CPU/MEM mini-bars), `overlay` (dim+compose a modal panel over a base view), `card`, `confirmmodal` (`ConfirmCard` — the minimal y/n confirm card `browse`/`nodedetail`'s cordon/drain verbs still use; `TypeNameModal` — 8b's type-the-name PROD delete confirm, the app's other red-bordered surface), plus `palette` (the one jump/namespace/context modal shell) as its own subpackage.
- **`internal/tui/tasks/*`** — one package per screen: `browse` (the one resting screen for every resource kind — table, health strip, filter, empty state; Deployments get a ROLLOUT/IMAGE column pair and `R` rollout-restart as of Phase 7; opening the CronJobs list starts not only CronJob's own lazy informer but Job's as well — `browse`'s CronJob branch lists Job once and aggregates it client-side into last-run/active-run/history rather than issuing a `ListRaw(Job)` per row, and `auxKinds` reloads the list on Job/Pod watch events too, so opening CronJobs must never make Job eager at connect and the live NEXT countdown must never poll), `poddetail` (5a pod detail — status/termination banner/meta grid/containers/bars/events/sidebar, pushed from `browse`'s Pods list and `nodedetail`'s pod rows on `↵`), `nodedetail` (11b node detail — conditions/allocated-allocatable/taints facts panel over the node's own pods table, pushed from `browse`'s Nodes list on `↵`), `yamlview` (8a read-only syntax-highlighted YAML view, pushed by `y` on any object from `browse`/`poddetail`/`nodedetail`; on a Secret it masks structurally — `secret.go` parses the YAML and replaces every `data`/`stringData` value and the last-applied-configuration annotation *before* marshalling the display text, so `Model.lines`, search and render never hold a value; never go back to masking by matching rendered lines, which missed every key YAML quotes), `podlogs` (5b streaming log viewer — toolbar with container/since/wrap/timestamps, severity-colored lines, restart boundaries, on Chrome v2 as of Phase 6; **it renders its viewport from a row index, never from the buffer** — `rowCounts`/`totalRows` say how many physical rows each of the 5,000 buffered entries occupies, so `visibleWindow` lays out only what's on screen and `maxVerticalOffset` is O(1). A whole-buffer `visualRows` pass in a render path is the regression to watch for: it cost 19.8 ms *per frame* and, since the root shell fans `ResourceChangedMsg` to the active task, was paid on every watch event with no logs arriving at all. The index is repaired in exactly one place — `syncLayout` at the top of `clampOffsets`, keyed on `{width, wrap, timestamps, filter}` — and the render path may only *read* it, falling back to the full pass when it's stale, because Render stays pure. `BenchmarkPodLogsRender` catches the regression without a cluster; see `docs/performance.md`), `events` (9b deduped, severity-colored event feed — hand-rolled two-line rows, not `components.Table` — namespace-scoped from `browse`'s `e` or object-scoped from `poddetail`/`nodedetail`'s `e`, `↵` jumps to the involved object via `tui.GotoResource` — the root's `routeGoto` pushes a fresh browse on top, so one `esc` returns to the feed, and a cluster-scoped target leaves `Session.Location.Namespace` alone), `execpicker` (10a exec container picker — pushed by `x` on a Pod with more than one container from `browse`/`poddetail`; a single-container pod execs immediately without this screen), `secretdata` (27b Secret Data view — masked KEY/VALUE/SIZE grid, `a` line-inserts a new key, `↵` on an existing row decodes and re-edits its real value, `D` removes one, pushed from `browse`'s Secrets list on `↵`), `configmapdata` (27a ConfigMap Data view — KEY/VALUE/SIZE grid, no masking since ConfigMap values aren't sensitive; `↵` edits a short value in place, `e` opens a multi-line buffer editor for a folded key, `ctrl+r` chains the apply with a rollout-restart of every consumer, pushed from `browse`'s ConfigMaps list on `↵`), `objectdetail` (14d generic CRD detail — meta grid from the kind's own printer columns, CONDITIONS, EVENTS, no per-CRD layout code ever, pushed from `browse`'s `↵` on any discovered CRD row), `overview` (19a cluster overview — capacity bars, nodes, cluster-wide trouble list, recent rollout changes; a routing layer, not the resting screen, reached only via `g "ov"`), `timeline` (16a/16b incident timeline — events, container restarts, and rollout revisions merged newest-first; namespace-scoped from `browse`'s `t`, object-scoped from `poddetail`/`nodedetail`'s `t`), `whocan` (22a RBAC who-can — resolves `(Cluster)RoleBindings`→`(Cluster)Roles` entirely from the informer cache, no server round-trip per query; the four RBAC informers it needs are lazy, so the first open of the screen fills them and reload lands via their change events; reached via `g "who"` or `w` from a 403 card), `routetable` (23a/23b Ingress/Gateway API routing table — one row per host+path or match, live backend resolution; pushed from `browse`'s `↵` on an Ingress or a discovered HTTPRoute/GRPCRoute/TCPRoute/Gateway kind), `forwardpicker` (13a port-forward picker — candidate ports discovered from the target object plus a trailing `+ other port` row that takes one the object never declared, in kubectl's own `local:remote` spelling, because a declared port is a hint and never a limit; `↵` starts the forward via `kube.ForwardManager` without suspending the program), `helmhistory` (18a Helm release revision rail — decoded straight from the release's own `helm.sh/release.v1` Secret, `R` rolls back through `kube.Mutator.HelmRollback`), `cronjobschedule` (36d schedule editor — one cron field decoded live into MIN/HOUR/DOM/MONTH/DOW plus a next-five-runs proof and an old/new firing-set WHAT CHANGES diff over the coming year; timezone editing is gated by the tri-state server-version capability rather than inferred, apply is a reversible `TierNone` patch with the source `resourceVersion` as a precondition and a one-step undo, `ctrl+y` escapes to the full YAML editor; pushed from `browse`'s CronJobs list on `S`), `cronjobdetail` (36e CronJob detail — facts grid, a last-terminal-failure band, and the associated Jobs table built from the same cache-local CronJob+Job aggregation `browse`'s CronJob branch uses, headed "associated with this cronjob" since manual Jobs are annotated rather than owned; ### The Task contract and navigation stack

`tui.Model` is the root Bubble Tea model. It wraps a single active `Task` and keeps a `stack []Task` for back-navigation:

- `Task` = `tea.Model` + `SetSize(w, h)`. Every screen implements it.
- When a task's `Update` returns a *different* task instance, the root pushes the current one onto the stack (this is how `browse` opens `podlogs` via the injected `OpenLogs` callback, on `l`).
- A `tui.BackMsg` pops the stack. Screens send `BackMsg` instead of quitting to return to the previous screen.
- The root also fans `tea.WindowSizeMsg` out to the active task's `SetSize`.

### Task package conventions

Each task package is split into files by responsibility: `model.go` (struct + `New`/`Init`/`SetSize`), `update.go` (message handling), `view.go` (rendering), `keys.go` (key bindings) — `browse` also has `sort.go`, `filter.go`, `selection.go`, `metrics.go`, and `hints.go` for its extra concerns. State is tracked with the shared `tui.TaskState` enum (`loading`, `ready`, `empty`, `error`, `permission-denied`, `confirming`, `success`, `cancelled`).

Mutating actions are designed to go through a `confirming` state before executing: screens embed an `actions.Controller`, press a mutating key → `Begin(actions.Request{Verb, Prod}, tui.TaskAction)` (Begin resolves the tier through `verbs.Resolve` — `TierNone` verbs like cordon execute immediately; `TierInline`/`TierModal` move to `confirming`), then every confirm key — y/N, type-the-name + `enter`, `esc`, the `ctrl+k` force-delete escalation — routes through the one `Controller.HandleConfirmKey` (its hints from `Controller.ConfirmHints`, both keyed from the verbs registry; never a per-screen `y`/`n` switch) to execution, and the `actions.ResultMsg` returned feeds `HandleResult`. Execution runs through `kube.Mutator`, so no screen calls a write verb directly. **Every outcome is shown, through one path:** `HandleResult`/`HandleBulkResult` (and `Begin`'s own refusals — offline, missing metadata) set `Controller.Result()`, every controller-embedding screen returns it from `ActionResult()` (`tui.ActionResulter`), and `tui.Frame` renders it on the keybar — a failure in `Theme.Bad` behind `✕`, replacing the hint groups and truncated rather than dropped; a success in `Theme.Good` behind `✓` on the right; a write still in flight after 1 s (writes have no deadline) shows `◌ … still running · Ns` dim in that slot until its result lands, carried by an `actions.RunningMsg` every screen must hand to `HandleRunning` and return its command, since that command is the only path the write's `ResultMsg` arrives by. Each screen calls `DismissResult()` at the top of its `tea.KeyPressMsg` case, so the line lasts until the user's next key; a screen whose spec gives the result its own surface (26a's will-run strip, 24a/25a/27a/27b/36d) calls `DismissResult()` right after `HandleResult` instead of rendering it twice. `actions/guard_test.go` fails any task package that embeds a Controller without all three. Results carry the `Begin`'s sequence number (`ResultMsg.Seq`), so a slow result from an earlier action (an in-flight cordon or drain) only reports its outcome line — it never clears a newer pending confirm. `browse`'s Nodes list and `tasks/nodedetail` call this for `C` cordon/uncordon (`TierNone`, no confirm) and `ctrl+d` drain (`TierModal`, still `components.ConfirmCard`'s minimal inline card, unchanged since Phase 9 — deliberately not upgraded to the type-the-name modal). `browse` (any row, any kind), `tasks/poddetail` and `tasks/objectdetail` call it for `D` delete, tier-driven through `verbs.Resolve`: inline `y/N` in non-prod, `components.TypeNameModal` when the active context is tagged prod or the kind is a Namespace/CRD/Node. `ctrl+k` (`verbs.ForceDelete.Key`) on a pending Pod delete escalates to force-delete at `TierModal` from either surface — outside PROD that turns the inline `y/N` into the type-the-name modal. `browse`'s own `m` labels/annotations editor (26a, `tasks/browse/meta.go`) is the first screen built to never let a commit close it: its `pendingMeta` gate stays set across the whole `Begin`/`Confirm`/`HandleResult` cycle (a join-locked edit's or a removal's `y/N` renders *inside* the still-open panel, not as a table-with-overlay), and `HandleResult` either re-fetches the object and refreshes the grid + shows an inline result line on success, or restores the exact pre-commit editing/add state with the server's error on failure — `esc` is the only thing that closes it. **"confirm → execute → refresh → show result → remain on screen" is the decided contract for every context-preserving inspector/editor, not just 26a** — docs/design README.md's §25a/§27a/§27b specify the same shape (SetResources' four-field apply, ConfigMap's per-key `↵`/`ctrl+r`, Secret's add-key flow). §27b is implemented (`tasks/secretdata`, pushed from `browse`'s Secrets list on `↵` — a full pushed screen with its own `› Data` breadcrumb segment, not a `browse`-embedded panel like 26a/25a, since the mockup's breadcrumb adds that segment past the object itself): `a` line-inserts a new key, `↵` on an existing row decodes its real value into the same visible-while-typing buffer for a rewrite (not a blind edit — an explicit departure from the original 27a-covers-editing split; a value that can't round-trip the single-line buffer — multi-line or binary, `textfield.RoundTrips` — is refused with an inline note rather than opened pre-flattened, and 26a refuses multi-line annotations the same way), `D` removes an existing key. All three follow the same confirm/refresh/remain contract; `ctrl+x` (not a bare letter) toggles the mask on whichever buffer is open, so plain `x` stays typeable; the will-run band itself is omitted entirely — no rule, no placeholder line — whenever there's genuinely nothing to preview, appearing only once there's a real command/confirm/result to show; the will-run line and every result message always mask/omit the value, success or failure. §27a is also implemented (`tasks/configmapdata`, the same full-pushed-screen shape as 27b): `↵` on a short value edits it in place, `e` opens a 17a-style buffer editor scoped to just that value (apply key is `alt+a`, not 17a's `ctrl+s` — `ctrl+s` is the terminal XOFF key in some environments, so this one buffer editor moved off it to `alt+a`, which avoids terminal flow-control keys), `ctrl+r` chains the apply with a rollout-restart of every workload named in the consumers strip, under `RolloutRestart`'s own friction (`verbs.RestartConfigMapConsumers`: inline `y/N`, the type-the-ConfigMap's-name modal in PROD); same confirm/refresh/remain contract as 26a/27b. Both 27a and 27b patch with the object's resourceVersion as observed when the buffer opened (`TaskScope.DataResourceVersion`) as a precondition, never the one a watch event refreshed mid-edit: a 409 keeps the buffer, says the object changed, reloads, and runs no `ctrl+r` restarts. §24a (`setimage.go`) and §25a (`setresources.go`) follow it too: a successful apply re-fetches into a fresh target and keeps the panel open with an inline result line (`handleSetImageResult`/`handleSetResourcesResult`), closing only if the object vanished from the lister; a failure keeps the attempted buffer with the error. Any of `meta.go`, `setimage.go`, `setresources.go`, `tasks/secretdata` or `tasks/configmapdata` is valid precedent for new work.

Namespace/context switching now dispatches for real: the root shell's `g`/`n`/`c` keys each open the one `components/palette` overlay (scoped Goto/Namespace/Context — `internal/tui/goto.go`/`namespace.go`/`context.go` build its `Item`s from `Session`), and `Enter` sends a navigation message (`GotoKindMsg`/`GotoResourceMsg`/`SwitchNamespaceMsg`/`SwitchContextMsg`) that the root `Update` uses to keep `Session.Location` authoritative before forwarding to the active task — `browse` handles all four. A context switch is the one that actually rebuilds the cluster: `kube.Cluster.SwitchContext` runs in a `tea.Cmd` (blocking, since it re-syncs the eager informer caches — the rest start again on demand, as at launch), so every `Session` read/write around it (recents, `PerContext` restore) happens synchronously *before* the `tea.Cmd` closure is built — the closure itself only touches the stable `*kube.Cluster` pointer. `?` opens a help overlay built from the active `Screen`'s own `Keybar()` (current-view column) plus `Session.HelpScope`/`HelpGlobal` (the fixed SCOPE/GLOBAL columns).

Dependencies are always passed via a package-local `Config` struct with interface-typed fields, and `New` fills in defaults for zero values. Follow this when adding a screen: define the interface you need in the task package, implement it on a `Client*` type in `kube`, and wire it in `app.NewModel`.

## Testing

Heavy use of table tests plus **golden-file** rendering tests under `test/golden/`, all following the same `UPDATE_GOLDEN=1`-guarded `TestGenerateGoldenFixtures` + comparison-test pattern:

- `internal/tui/components` (the `Table` component itself) against `test/golden/table/*.golden`.
- `internal/tui/tasks/browse` (full-screen 2a renders, 120×36 and 80×24) against `test/golden/browse/*.golden`, plus **forced-truecolor goldens in both themes** (`test/golden/browse/120x36-{dark,light}.golden`, ANSI included) — the fixtures that actually pin the Theme-token-to-cell color mapping, since the plain goldens render colorless under test. This is the pattern to copy for new theme-sensitive screens (`truecolorGoldenFixtures` in `browse/golden_test.go`): force the profile with `lipgloss.SetColorProfile(termenv.TrueColor)` + deferred restore. The profile is a global, so packages with truecolor goldens must not use `t.Parallel` in tests that render.
- `internal/tui/tasks/podlogs` against `test/golden/podlogs/`.

Anything about *what the app fetches* is tested against the fake clientset's recorded actions rather than through the UI (`internal/kube/lazy_test.go`, `helm_secrets_test.go`): assert which resources were listed, how many times, and with what field selector. That's the only way to catch a regression that renders identically but pulls the cluster down the wire — and when adding one, check it fails without the fix, since a test helper that builds its own informer factory can pass while proving nothing (hence `newTypedFactory`). `go test -race ./internal/kube` covers the lazy-start path, which is called from the Bubble Tea update loop while informers run on their own goroutines.

**End-to-end tests live behind the `e2e` build tag** (`test/e2e`, plus `internal/kube/e2e_lazy_test.go` which needs the unexported `kindInformers` map) and so never run under `go test ./...`. Run them through `./scripts/e2e-run.sh`, which provisions the kind cluster and fixtures, runs both E2E packages, and tears the cluster down even on failure. Pass ordinary `go test` flags through it for a focused run; use `KUTE_E2E_KEEP=1` to retain a failing cluster or `KUTE_E2E_REUSE=1` to use one already provisioned. The underlying kind cluster is required because a real kubelet is what makes logs/exec/port-forward genuinely testable — kwok is only the scale substrate. See `docs/e2e-testing.md`. The harness drives the *real* `app.run` through a real `tea.Program` over pipes, and captures frames via `tea.WithFilter` rather than by parsing output — bubbletea's renderer emits cursor-relative diffs, which no amount of ANSI stripping turns back into a screen. Two rules keep it from going flaky and both are load-bearing: **no golden files** (a real cluster produces nondeterministic AGE, pod-name suffixes, IPs and node assignment — E2E asserts substrings and structural predicates, goldens stay the unit-level tool), and **no one-shot assertions** (caches fill asynchronously, so every check goes through `App.WaitFor`/`WaitLoaded`/`Never`, which poll against a deadline while pumping the event loop; a bare `strings.Contains` on the first frame is a race by construction, and a one-shot check for a *negative* passes simply by looking too early). A third rule earned the hard way: **never assert on transient state** — polling can't help when the value itself comes and goes. A crash-looping container reads `CrashLoopBackOff` only while it waits, and the list redraws only on a watch event, so a frame captured mid-restart holds a stale word for as long as the backoff (capped at five minutes); assert the durable statement of the same fact instead. Likewise wait for a *row* before pressing `↵`, not for the breadcrumb, which is on screen before the rows are. A fourth: **never wait on a string the screen you're leaving also shows** — navigation is dispatched as a `tea.Cmd`, so the frame a key press fences on can still be the old screen, and `WaitFor` returns on it, aiming everything after at a screen that's being replaced. That's why `gotoKind` waits for the destination list's *title* and `backToPodDetail` for `CONTAINERS`, never for a row or object name both screens carry (`shop` is an Ingress *and* the middle of the Secrets list's `sh.helm.release.v1.shop.v2`). A fifth: **a key press whose meaning depends on the previous write fences on the screen, not the API** — reading the object back through a client proves the *server* has the write, not that kute does, and browse reloads from its informer cache on a 250 ms debounce. §30a's `s` is one verb in two directions and takes its direction from the projected row, so a press inside that window re-sends the write kute just made: no field changes, the server answers 200 without a resourceVersion bump, no watch event follows, and the test waits out its whole budget for the opposite verb (`flux_test.go`'s `waitForRowState`). No E2E test may call `t.Parallel`: `Launch` isolates `HOME`/XDG with `t.Setenv`, and `internal/kube`'s own e2e tests set the kubeconfig path, both process-global.

When you change rendering output, regenerate with `UPDATE_GOLDEN=1 go test ./path/to/package` and review the diff rather than hand-editing fixtures. Tasks are tested by driving `Update` with synthetic messages and asserting on `View()`/`Render()` output or state — no live cluster needed because all `kube` access is behind interfaces (see `browse`'s `fakeLister`/`fakeMetrics` test helpers, or `kube/fake` for a whole-cluster fixture set).
